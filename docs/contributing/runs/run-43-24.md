Roadmap-usb4 tasks 43.24 (Windows 8 and 8.1, the connection manager),
43.31 (`xhci98.sys` opted into on 8 and 8.1) and 43.37 (Windows 10), run
as one workstream on branch `p43-24`, one guest at a time. This sheet
records what each leg did and every reading; the roadmap's task lines say
what is ticked. Runtime, QEMU under TCG on development host A, the host
loaded by other agents' guests and builds throughout (the coordinator's
note of the day: CPU near 97 %), so no reading here is a timing beyond
the second.

### Hibernate: bug check 0x9F with the connection manager installed

On Windows 8 x86 every hibernate with this package installed ended in
bug check 0x9F, parameter 1 = 3 (a device object held a power IRP past
the timeout), and the next start in "Windows failed to resume from
hibernate with error status 0xC0000001": three times on 8 x86 (03:14 and
03:26 with the enclosure attached, 04:08 without it), once on 8 x64.
Controls on the same 8 x86 image without the package, booted on the same
command line: hibernate and resume passed with the tablet alone, and
passed with the Alpine Ridge tree and the enclosure attached (the NHI at
Code 28), both resuming to the lock screen with the leg's script
continuing after its `shutdown /h`.

The kernel dump of the third (`C:\Windows\MEMORY.DMP`, a bitmap dump,
read by a file-only script on the host that walks the PAE tables to the
devices named by the bug check's parameters; nothing executed):

| | |
|---|---|
| Parameters | `0x9F (3, 85078a50, 80c16b40, 85072be8)` |
| Parameter 2's stack, bottom up | `\Driver\pci` (PDO) <- `\Driver\ACPI` <- `\Driver\pci` (a bridge's FDO) <- **`\Driver\xhcicm`** (the tunnel-port filter) |
| Parameter 4, the IRP | `IRP_MJ_POWER` / `IRP_MN_SET_POWER`, `Type` DevicePowerState, `State` D0, `ShutdownType` 2 (PowerActionHibernate), its current location `xhcicm`'s, control `0xE1` |

That is the filter's own hold: `CmFilterPower` (`src\cm\cm_filt.c`)
returns `STATUS_PENDING` for a device D0 request on a bridge when
`CmRegHoldD0` keeps it for the NHI's resume (design record 21 section
6.3). Windows 8 sends that D0 during the hibernate transition itself, and
the NHI's resume that would release it does not come before the system
sleeps. A driver defect, not a text change: reported, not fixed (owner
question 1). Not read: the same on 8.1, 10 or 7 (43.21's 7 x86 hibernate
on the Ice Lake model resumed; why 7 does not meet the hold is not read), and the x64 dump.

## Findings

1. **Hibernate on Windows 8 bug-checks 0x9F in the tunnel-port filter**
   (43.24's resume clause): `CmFilterPower` / `CmRegHoldD0` keep a
   bridge's D0 `IRP_MN_SET_POWER` sent during the hibernate transition
   (`ShutdownType` PowerActionHibernate) for an NHI resume that never comes
   before the system sleeps; 8 x86 three times (dump read), 8 x64 once,

   reported, not fixed. The release notes' known limitations and the
   installer's readme now say not to hibernate 8 with the connection

2. **The first uninstall of the USB drivers stops part-way on 8.1 x64,
   8.1 x86, 10 x86 and 10 x64** (43.31 and 43.37's uninstall clause; it did not

**A first fix was wrong.** `af5f2a1b` (dropped from the branch, kept as
`p43-24h-a1`) held the D0 only once the system was working again, on the
reading that Windows 8 sends a bridge's D0 inside the transition. With it,
8 x64 and 10 x64 still stopped with 0x9F (3) at the resume from
hibernation, and 10 x64 stopped at the start after Fast Startup. The 8 x64
kernel dump (`MEMORY.DMP`, read on the host by a file-only parser) showed
the following:

- The blocked IRP was the tunnel port's (02:01.0) device D0. It was held
  on `xhcicm`'s filter, at the top of the bridge's stack, with the filter's
  last system state S0, `Held` 1, `InFlight` 1, and the watchdog running.
- The NHI's log ended at `cm.suspend=00000005` and the hold's bound lines.
  Its counters read suspends 1, resumes 0.
- The emulator's trace of the resume attempt has no `driver ready`.

So the held D0 was the resume's own. The NHI never resumed to release it.
The power manager resumes the non-pageable devices (the bridges) before
the pageable ones (the NHI, `DO_POWER_PAGABLE`), and `pci.sys` completes a
bridge's S0 only once its D0 has completed. The hold therefore deadlocks
the resume on 8 and later. The 43.21 and 43.44 legs (2026-10-22) had read
hibernation with the hold working on XP x64, Vista and 7.

**The fix, `925b3da7`.** Below NT 6.2 the hold is unchanged. From 6.2
(the kernel's own version, read from the shared user data page, since the
WDM version cannot tell 8 from 7), a marked bridge's D0 is passed down at
once and logged as `cm.reenum.hold.passed`. The NHI's release then
invalidates each such port, whether its resume succeeded or failed.

- Host vectors: `test_cm_ports.c`, 204 checks, 0 failures.
- `build-driver.cmd all` and `all -amd64` passed every gate.
- Reviewed and revised until the review converged. The first round found
  that `IoIsWdmVersionAvailable(6, 2)` tests the WDM version, which is
  6.0 on 8 to 10, so the gate was moved to the kernel's version. The
  second round's nit, record 22's wording of U15, was fixed. The third
  round was clean.
- Records 21 (section 6.3) and 22 (resume ordering, U15) are amended.

The legs with the fix follow.
