# Design Docs

Detailed design documents for this project, one per topic.

Naming convention: `NN-<what-it-is-for>.md`, a two-digit running-number prefix
in creation order followed by a short kebab-case description of what the
design is for. Do not put a phase number in the filename, since a design doc
may span or outlive a phase; note any phase association in the doc's title or
body instead. Add each new doc to the index below.

## Index

- [01-hardware-qualification-tool.md](01-hardware-qualification-tool.md) - DOS bare-metal Phase 0 tool that qualifies a candidate xHCI machine (BIOS handoff, bus-master DMA, INTx-in-PIC interrupt delivery, port topology/quirks) before any driver effort is spent on it. The verdict is per-controller and covers both targets; the machine needs neither OS installed.
- [02-hub-topology-route-string.md](02-hub-topology-route-string.md) - How the miniport learns hub topology (Phase 7, groundwork in Phases 3/6). xHCI needs Route String, parent-hub Slot ID and TT fields that the EHCI-era `usbport.sys` was never designed to provide; covers the hub-request-snooping design and the spike logging that must settle it.
- [03-host-unit-tests.md](03-host-unit-tests.md) - Host-side unit tests for the pure xHCI core (Phases 3/4 onward). Keep TRB encoding, ring/cycle logic, and context builders DDK-free so golden-vector tests catch bit-packing bugs in seconds instead of target reboot loops. Defines the source-layout rule, the test areas, and what stays VM-only.
- [04-controller-common-buffer.md](04-controller-common-buffer.md) - The Option A DMA-memory model (Phase 3 task 2, consumed by Phases 4 and 6): why `MiniPortResourcesSize` must be a worst-case reservation with a refusal path, the declared slot/scratchpad caps and what they cost, the region map and its Table 6-1 proofs, what the two shipping `usbport.sys` binaries actually guarantee about 32-bit DMA and page alignment, and why device contexts and EP0 rings cannot live in an endpoint buffer usbport discards during `ReopenPipe`.
- [05-locking-model.md](05-locking-model.md) - The miniport's complete synchronisation design (Phase 4 task 9, consumed by Phases 5-8): the four unsynchronised contexts `usbport.sys` calls from, why one innermost driver-image lock is the answer, the lock order, the DIRQL exception and how the ISR is made to need no exclusion, the static review of every entry point with the four defects it found, and where Phase 5's port state and Phase 6's transfer metadata go before they are written.
- [06-device-matrix-verdict.md](06-device-matrix-verdict.md) - What a device row in the automated VM matrix must state, and how a pass or fail is decided from it (Phase 10 task 10.2, consumed by tasks 10.3-10.5): the five outcomes and why `NODRIVER` and `INERT` are results rather than silences, the counter that separates "this driver enumerated it" from "the OS claimed it", the five kinds of expectation and why `zero` and `inert` may never be interchanged, the identities that outrank the counters, and the four traps the harness enforces in code rather than in a comment.
- [07-controller-recovery-in-place.md](07-controller-recovery-in-place.md) - How a controller this driver declared failed comes back without a stop/start (Phase 13 batch 13-R, task 13-R.1): why "recovery is a stop/start" stopped being a design once both shipping `usbport.sys` builds were censused and found never to issue one, the two candidate repairs and why degrading in place was insufficient on the evidence, the request/arm/perform split forced by which usbport lock each context holds, the `InitBelowPassive` IRQL contract and the five sites that read it, where the latch is released and why there, and the SMP window this narrows rather than closes.
- [08-build-flavours-and-the-log-channel.md](08-build-flavours-and-the-log-channel.md) - Why `release`/`debug`/`qemu` are three flavours and not two, and what a Windows 98 user can therefore send back (Phase 13 batch `13-L`, task 13-L.0, feeding task 14.0).

  The two stacked answers to "why can other Win98 drivers log when this one cannot": usbport takes `IRP_MJ_CREATE`/`CLOSE`/`DEVICE_CONTROL` on the miniport's driver object so there is no ring-3 door (permanent), and the published debug binary did not load on Win98 metal, with the QEMU port-`0xE9` import as its sole import delta (this project's own defect; why that build failed is not established).

  Also the `DBG`/recording/emission axis that one switch conflates, why the safe configuration must be the default rather than the opt-out, the seven places the two-flavour assumption is wired in, and why the registry was investigated and is not the plan.

  Section 13 is a later addendum (task 13-L.2): the PassThru read channel promoted into every shipping flavour, the verbosity ladder that replaced sink-gated recording, the file sink's retirement, and the security posture. `docs/contributing/passthru-snapshot-instrument.md` is its as-built companion; this record owns the "why" and that one the "what".

- [09-post-release-unattended-run.md](09-post-release-unattended-run.md) - What an automated run on freshly installed Windows 98 SE and Windows 2000 SP4 guests has to do after a release (Phase 16, task 16.1, added after the cut as task 14.3): the decisions the project owner took (both targets single-processor, so Phase 2d's SMP guest is out; the single manual driver install against a base image cloned from the pre-driver snapshots and stamped with the version it carries; the `qemu` flavour only, the `release` binary being the physical machine's reading; the qualifier and log channel out of scope; the replug leg judged from counters; storage enumerated but not round-tripped; TCG with no time budget until one is measured), what separates this from Phase 10's matrix and from the hand-run acceptance of a published release, what this QEMU build cannot present and must therefore record as not reached, the refusals that belong in code, the preparation procedure, and the report header that makes two releases' runs diffable.
