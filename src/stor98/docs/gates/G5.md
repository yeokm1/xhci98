# Gate G5: memory lifetime at stop

> Prototype source is not on `main`; it stays on the gate branch. Branch `phase0-g5g7`: commits 316bd25 (debug-port layer) and b3ae1ef (no `ScsiRestartAdapter`, bounded stop path, memory probe `src/g57probe.{c,h}`). Shared with [G7.md](G7.md).
>
> Windows 7 x64 run (fail for removal, as on 2000 and XP x64; the driver-owned contiguous pool survives): [Q-NT.md](Q-NT.md), item 1.

PLAN 0.0, G5: does the port free or reuse the uncached extension (and the SRB extensions)
after `ScsiStopAdapter` for removal, rebalance and power, and when relative to the
callback's return? Does it call the stop in a context where a longer bounded poll is
acceptable?

**Pass condition:** either the port keeps the memory while the controller has not
acknowledged disable, or the stop path always obtains evidence within its budget (RDY=0
within budget on every tested controller model, or a G3 link-down notification already
received; all-ones reads do not count).

**If it fails:** the stop path cannot be made DMA-safe on that port; the port is blocked
pending a maintainer decision.

Date: 2026-10-15. Prototype: branch `phase0-g5g7`, commit b3ae1ef on 316bd25 (debug-port
layer). 9x is covered by the G9 report (`phase0-g9`, `docs/gates/G9.md`, "G5 on 9x").

## Verdicts

| OS | Orderly stop (Device Manager disable), RDY never clears | Surprise removal, then OS removal | Power stop (hibernate) | Resource rebalance | Verdict |
|---|---|---|---|---|---|
| XP x64 SP2 (i440FX, TCG) | `ScsiStopAdapter` called; not acknowledged; **uncached extension, SRB extensions and device extension freed and reused** (NTFS pages, within 15 s); image unloaded | **No `HwAdapterControl` call at all**; all three freed and reused; a late CQE from a held command landed in a reused NTFS page | kept: same device extension (not zeroed), same uncached VA and PA, sentinel intact | not triggered | **FAIL** for port-owned memory |
| Windows 2000 SP4 (i440FX, TCG) | same as XP x64 (reused by NTFS `INDX` pages within a minute) | same as XP x64: no callback; late CQE landed in a reused NTFS `FILE` page | kept, as XP x64 | not triggered | **FAIL** for port-owned memory |
| Windows 7 x64 | not run (time) | | | | open |
| XP x86, Vista | not run (no VM in this session) | | | | open |

Neither clause of the pass condition holds on 2000 or XP x64 for memory the port allocates:
the port frees it whether or not RDY=0 was acknowledged, and on surprise removal it frees it
without calling the miniport at all, so a stop path that "obtains evidence within its
budget" does not even run. Under the PLAN consequence both ports are **blocked pending a
maintainer decision** for any design that keeps DMA-reachable memory in the uncached
extension.

The measured way out (for the maintainer's decision, below): DMA-reachable driver memory
allocated **outside the port** survived every stop, removal and image unload in these runs
and can be quarantined. It is the NT analogue of the `_PageAllocate` pool G9 proposes for 9x.

## The prototype

`src/g57probe.{c,h}` (built with `NVME98_DBGPORT=1 NVME98_G57=1`, NT targets only;
throwaway) on top of the base driver:

- Reports through the usb4-emu debug port (stage codes 0x80-0x89): the device extension VA
  and PA, the uncached extension VA and PA, the first SRB extension VA and PA, the I/O CQ PA,
  and per `HwFindAdapter` whether the device extension still carries the probe's magic (not
  zeroed), whether the uncached extension is at the same PA and VA as before, whether its
  spare last page still holds the previous sentinel (read before the base zeroes it), and
  whether the previous uncached VA is still mapped (`MmIsAddressValid`).
- Sentinels: the uncached extension's spare last page (`G5SN`, generation, `0xDEADBEEF`, ...;
  first dword rewritten `G5ST` at stop).
- Quarantine-pool candidate: 16 KiB from `MmAllocateContiguousMemory` (below 4 GiB) at the
  first `HwFindAdapter` of the image, filled with `G5QP`/`0x5A5A5A5A`, never freed.
- `ScsiStopAdapter` runs the stop path of PLAN 0.10 within the stall budget: mask INTMS,
  cancel the fallback timer, CC.SHN normal and up to 4 x 100 us polls of SHST, CC.EN=0 and
  up to 4 x 100 us polls of RDY, no queue deletion (so a held command survives); it records
  whether RDY=0 was acknowledged.
- `ScsiRestartAdapter` is not advertised (G7).

Host side: the QEMU monitor reads the reported physical pages (`xp`) and translates the
reported VAs (`gva2gpa`) after each stop; harness faults (usb4-emu `docs/HARNESS.md`):

- `x-rdy-clear-delay-ms=-1`: the disable is never acknowledged (the controller has reset;
  only CSTS lies).
- `x-faults=at=fetch op=read act=hold ...`: a read held unexecuted inside the controller.
  The port's own timeout reaches `HwResetBus`, which in the base completes everything
  (unsafe by design, PLAN 0.10, but it lets the run continue); the command stays live in the
  controller. With `release=rdy0-ack` the CC.EN=0 write of the stop is deferred, so the
  controller really keeps running with its queues: the "not isolated at stop" case.
- `x-gate=reads-fail`: config and MMIO read all-ones and writes are dropped, but the DMA path
  stays open and the endpoint is not reset (the presence-lost-with-DMA-open case). Then a PnP
  rescan (`g57dev rescan`) makes the OS find the function gone.
- `x-release=tag:...`: the held command executes: its data and CQE are written to the old
  addresses.

## Evidence

All under usb4-emu `vms/nvme98-g57/` (local): decoded debug-port logs in `evidence/*.txt`
(decoder `evidence/g57log.py`), trace excerpts `evidence/*-trace-excerpt.txt`, CQ page dumps
`evidence/*-cq-*.txt`, raw `logs/`, screenshots `shots/`.

### XP x64

1. **Disable with RDY never clearing** (`logs/dcon-xp-a1.log`, `evidence/xp-a1.txt`). The
   first disable reached the NVMe through its parent (the tunnel bridge was disabled too, a
   tool quoting slip), the second was the NVMe alone; both behaved the same.
   `ScsiStopAdapter`: CSTS=1, SHST complete (0x9), RDY still 1 after the budget, acked=0.
   2-4 ms after the callback returned, PCI.sys wrote the command register to 0x100 (Bus
   Master and Memory Enable cleared) and PMCSR to D3hot (0x0B). The uncached extension
   (PA 0x06AD7000) had been reused by the first check, about 15 s after the stop: its spare page and the old I/O CQ page held
   NTFS `FILE` records, its first page kernel pointers. The VAs still translated (the pages
   were reused, not unmapped), so `gva2gpa` is not a free detector; content is.
2. **Re-enable**: `DriverEntry` ran again with fresh static data (the image had been
   unloaded); new device extension, new uncached extension (PA 0x06F16000). The old
   quarantine pool (PA 0x06CD2000, allocated by the unloaded image) was intact.
3. **Not isolated at stop, orderly path** (`release=rdy0-ack` hold, RDY never clears):
   the CC.EN=0 write was deferred (`usb4_h_defer ... deferred`), the controller kept the
   held read. After the stop, PCI.sys again cleared Bus Master Enable. Releasing the read
   then failed in the model: `pci_nvme_err_addr_write addr 0x6f23350` (the CQE) and CFS.
   The old CQ page was unchanged (`evidence/a2-cq-*.txt`). So on the orderly path the
   OS's own BME clear stopped the late DMA in this model; it is not driver-visible evidence
   (the miniport has no config access after the stop), and the order between the port's
   free and PCI.sys's BME write is not observable from the host (the window is at most the
   2-4 ms between them).
4. **Surprise removal with the DMA path open** (`logs/dcon-xp-b.log`,
   `evidence/xp-b*.txt`): a read held, `x-gate=reads-fail`, `g57dev rescan`. The NVMe
   devnode disappeared. **No `HwAdapterControl` call of any type reached the miniport**
   (no stage after `HwResetBus`). Afterwards the old uncached spare page and I/O CQ page held
   NTFS log records (`RCRD`) and the device extension's page other pool data. Releasing the
   held read wrote its CQE (CID 0xFD, SQ head 0x14) at 0x06F34138, **inside a reused NTFS log
   page** (`evidence/b-cq-before.txt` vs `b-cq-after.txt`), and its 4 KiB of data to the old
   caller buffer. The quarantine pool was intact.
5. **Hibernate** (`evidence/xp-h1.txt`, `xp-h2*.txt`): `ScsiStopAdapter` at power-down,
   acknowledged (RDY=0). On resume the next `HwFindAdapter` saw the same device extension,
   not zeroed (`DEVEXT_KEPT`, `STOPPED_BEFORE`), and the uncached extension at the same VA
   and PA with the old sentinel intact (`SAME_PA SENTINEL_KEPT OLD_VA_VALID SAME_VA`), over
   three hibernate cycles. See G7.

### Windows 2000

1. **Disable with RDY never clearing** (`evidence/w2k-a1.txt`): as XP x64. acked=0; PCI.sys
   cleared Bus Master Enable and set D3hot 3 ms after the callback; the SRB extension page
   and the device extension were reused at once, the uncached extension (PA 0x01818000)
   within a minute (`INDX` records in the spare page and the old CQ page). Re-enable reloaded
   the image (`DriverEntry` count 1). The quarantine pool (PA 0x01828000) was intact.
2. **Surprise removal with the DMA path open**: no `HwAdapterControl` call; the device
   extension reused at once, the uncached extension after some file-system activity
   (`FILE` records). The released read's CQE landed at 0x01646398 **inside a reused NTFS
   MFT page** (`evidence/w2k-b-cq-*.txt`). Quarantine pool intact.
3. **Hibernate** (`evidence/w2k-h2*.txt`, `w2k-h4*.txt`): as XP x64: stop acknowledged,
   device extension and uncached extension preserved across the cycle.

### Layout facts (both)

- The SRB extensions live in the same port common buffer as the uncached extension: XP x64
  puts them directly after it (uncached + 0x10000), 2000 directly before it (one page below).
  They share its lifetime.
- The device extension is pool memory; it is freed on removal and reused immediately.

## Answers to the gate's questions

| Question | XP x64 | 2000 |
|---|---|---|
| Uncached extension after a removal stop | freed and reused (within 15 s) | freed and reused (under a minute) |
| ... after a surprise removal | freed and reused; **no stop callback** | same |
| ... after a power stop | kept, same VA/PA, contents preserved | same |
| SRB extensions | same common buffer as the uncached extension, same lifetime | same |
| Device extension | freed on removal, kept (not zeroed) across power | same |

| Stop-callback context / longer polls | not measured (IRQL not instrumented); the 0.8 ms budget poll was used | not measured |

## Consequence and decision needed

Per PLAN, both ports are blocked pending a maintainer decision (recorded under "Maintainer
decisions" as the conditional entry for G5). Two facts shape the options:

- The stop path cannot protect port-owned memory: on surprise removal there is no stop
  callback at all, and on an orderly stop the port frees the memory regardless of the
  acknowledgement.
- Memory the driver allocates itself, outside the port, is not freed by anything the OS does
  to the device or the image.

**Proposed option (needs the maintainer's decision):** keep every DMA-reachable driver
structure (admin and I/O queues, PRP list pages, bounce buffers) in a driver-owned
contiguous pool allocated with `MmAllocateContiguousMemorySpecifyCache` (non-cached, below
the DMA limit 0.8 negotiates; below 4 GiB on x86) at the first `HwFindAdapter`, with physical
addresses from `MmGetPhysicalAddress`. The pool is released (`MmFreeContiguousMemory`) only
with isolation evidence (0.10), and leaked (quarantined) otherwise, including at every
surprise removal. The uncached extension shrinks to what the port insists on, or zero.
Costs and risks to weigh:

- A SCSI miniport that imports ntoskrnl directly is outside the SCSIport miniport contract
  (it works on 2000 and XP x64 in these runs; 7 x64 untested). It also bypasses the HAL DMA
  adapter: correct on x86/x64 without an IOMMU and with Dma64BitAddresses honoured, but the
  32-bit-only and PAE cases need the address limit enforced by the allocation itself.
- A pool that outlives the image needs a home that survives `DriverEntry` running again
  (the image's static data is lost): on re-arrival the old pool is unknown to the new
  image, so each quarantine leaks its pool for the rest of the boot (16-64 KiB per event).
  Finding it again would need a registry or named-object handle, which is more kernel
  surface. Leaking is the simple and safe default.
- The callers' buffers are a separate matter: after a surprise removal they are retired by
  the port without any callback, which is G2/G4/MD-1 territory, not G5. This run shows the
  hazard is real when the DMA path is open (the CQE and 4 KiB of read data landed after the
  port had released everything).

The alternative the PLAN already names (block the port) would leave 2000 and XP x64 without
surprise-removal support.

## Proposed PLAN changes (not applied here)

- 0.0 G5 row: record the result above; "the port keeps the memory" is false for removal on
  2000 and XP x64, true for power.
- 0.4 and 0.5: bounce buffers, PRP list pages and queues move out of the uncached extension
  into the driver-owned pool if the maintainer takes the option above;
  `ScsiPortGetPhysicalAddress(..., NULL, ...)` is then no longer the translation route for
  them.
- 0.10 stop: "where the port keeps the memory (G5)" never applies on NT for removal; the
  quarantine works only for the driver-owned pool.
- 0.11 matrix, "Stop with device already absent": on 2000 and XP x64 a surprise removal
  produces **no** `ScsiStopAdapter`; the row's callback column is "none". Teardown
  invariants (timer unable to rearm, interrupts masked) cannot be enforced from a callback
  there; what the port does with a pending `RequestTimerCall` at removal is still to be
  measured.
- 0.11 matrix, orderly stop: note that PCI.sys clears Bus Master Enable and sets D3hot just
  after the callback returns (measured, not evidence the driver can use).
- Maintainer decisions: add the conditional G5 entry for 2000 and XP x64 with this result.
