# Gate G8: final shutdown trigger

> Prototype source is not on `main`; it stays on the gate branch. Branch `phase0-g1g8`: commits 316bd25 (debug-port layer) and 759d860 (prototype), as for [G1.md](G1.md).

PLAN 0.0, G8: for each OS and each `CachesData` setting, which callback arrives after the
last I/O at system shutdown, hibernate and Device Manager disable (`ScsiStopAdapter`,
`SRB_FUNCTION_SHUTDOWN`, a 9x IOS or Configuration Manager event)?

**Pass condition:** a final trigger is identified for each OS and recorded in 0.11.
**If it fails:** CC.SHN is issued on the last shutdown notification seen, and any later
I/O re-enables the controller first (tested).

Date: 2026-10-14/15. Same prototype, VMs, launchers and decoder as [G1.md](G1.md) ("Setup").
Every `HwStartIo` entry, every I/O completion, `SRB_FUNCTION_SHUTDOWN`/`FLUSH`, SYNCHRONIZE
CACHE, every `HwAdapterControl` call, the stop path, and any request after a shutdown SRB
write a debug-port stage (`src/dbgport.h`, codes 0x10, 0x21, 0x60-0x69), so the host trace
records their order together with the NVMe commands they cause. `CachesData` was switched
with the registry `DriverParameter` `cd=1` (read in `HwFindAdapter`, applied by a Device
Manager disable/enable or a restart). The driver keeps the inherited behaviour for these
events (SHUTDOWN and FLUSH SRBs and SYNCHRONIZE CACHE each become one NVMe Flush; the stop
path deletes the I/O queues, sets CC.SHN, waits for SHST, clears CC.EN); MODE SENSE reports
WCE=1. Before each run `w.cmd` wrote fresh files to the NVMe volume (dirty data).

Windows 2000 ran on i440FX with `acpi=off` (Standard PC HAL); XP x64 on i440FX with ACPI;
Windows 7 x64 on q35 with ACPI.

## Observed order (after the last ordinary I/O)

`SYNC` = SCSI SYNCHRONIZE CACHE(10), `FLUSH` = `SRB_FUNCTION_FLUSH`, `SHUTDOWN` =
`SRB_FUNCTION_SHUTDOWN`, `W` = writes, `Stop` = `HwAdapterControl(ScsiStopAdapter)`.

| 2000 | Restart | as shut down (last SYNC) | as shut down (two SHUTDOWNs, I/O between) |

| XP x64 | Restart | SYNC, W, **SYNC** | SYNC, FLUSH, W, SYNC, **SHUTDOWN** |

## Final trigger per OS

| OS | Shut down / restart | Hibernate | Device Manager disable |
|---|---|---|---|
| 2000 | **none identifiable.** `CachesData` FALSE: only SYNCHRONIZE CACHE, the last one indistinguishable from earlier ones. TRUE: two `SRB_FUNCTION_SHUTDOWN`, with reads and writes between them | `ScsiStopAdapter` | `ScsiStopAdapter` |
| XP x64 | `CachesData` TRUE: `SRB_FUNCTION_SHUTDOWN` (one, nothing after). FALSE: none identifiable | `ScsiStopAdapter` | `ScsiStopAdapter` |
| 7 x64 | `CachesData` TRUE: `SRB_FUNCTION_SHUTDOWN` (one, nothing after). FALSE: none identifiable | `ScsiStopAdapter` | `ScsiStopAdapter` |

## Verdict

- **Hibernate and Device Manager disable: PASS on 2000, XP x64 and 7 x64**, either
  `CachesData` setting: the final trigger is `ScsiStopAdapter`, with nothing after it.
- **Shut down and restart: FAIL on 2000** (either setting) **and with `CachesData` FALSE on
  XP x64 and 7 x64.** No `ScsiStopAdapter` arrives at shutdown or restart on any of the three
  NT ports (the PLAN 0.11 expectation "`ScsiStopAdapter` at power-off" is refuted), and with
  `CachesData` FALSE the miniport receives no shutdown notification at all. With
  `CachesData` TRUE, XP x64 and 7 x64 sent exactly one `SRB_FUNCTION_SHUTDOWN` as the last
  request (a pass for those two only with `CachesData` TRUE); Windows 2000 sent two, with
  ordinary I/O after the first, so the first is not final and the second cannot be
  recognised as the last when it arrives.
- 98 SE and ME (IOS / Configuration Manager events, `HwAdapterState`) were not run here; the
  G9 agent owns 9x. XP x86, Vista and 7 x86 were not run.

Consequence (G8 failure branch, as written): issue CC.SHN on each shutdown notification
seen, and re-enable the controller (fresh bring-up of PLAN 0.10) if any I/O follows; this
must be tested on 2000, where I/O does follow. That consequence requires a shutdown
notification to exist, i.e. `CachesData` TRUE (see "Plan changes").

## Other findings

- `SRB_FUNCTION_FLUSH` reaches the miniport only with `CachesData` TRUE, and then pairs with
  SYNCHRONIZE CACHE (2000: both every time; XP x64 and 7: at shutdown/restart, XP x64 also at
  hibernate). Neither ever arrived from a Device Manager disable on XP x64 or 7.
- On XP x64 and 7, **Device Manager disable sends no flush of any kind before
  `ScsiStopAdapter`**, even with WCE=1 reported and with `CachesData` TRUE: data written just
  before is protected only by what the stop path does (here CC.SHN, which completed with
  SHST=10b in every run). Windows 2000 does send SYNCHRONIZE CACHE before the stop.
- Hibernate always sends START STOP UNIT (stop) between the last SYNCHRONIZE CACHE and
  `ScsiStopAdapter`; the base completes it as a no-op.
- The inherited stop path worked in every run here (queues deleted, SHST complete within
  3-13 ms, RDY=0), but it still polls in 1 ms stalls up to seconds (PLAN 0.10 stop is the
  fix; outside this gate).

## Plan changes this implies (for the maintainer)

1. **PLAN 0.11, `CachesData`:** "stays FALSE" leaves the miniport with no shutdown
   notification at all on 2000, XP x64 and 7 x64; durability at shutdown then rests on
   SYNCHRONIZE CACHE (sent on every port, mapped to NVMe Flush) and CC.SHN is never issued
   at OS shutdown or restart (only hibernate and disable reach the stop path). Either set
   `CachesData` TRUE on NT so `SRB_FUNCTION_SHUTDOWN` arrives and apply the G8 consequence
   (CC.SHN on each, re-enable on later I/O, needed on 2000), or keep FALSE and accept that
   the SSD sees every shutdown as unsafe (data is flushed, CC.SHN is not). This needs a
   maintainer decision; both options keep the flush.
2. **PLAN 0.11 "Final shutdown trigger" row:** replace "expected on NT: `ScsiStopAdapter`
   at power-off" with the table above: `ScsiStopAdapter` for hibernate and disable;
   `SRB_FUNCTION_SHUTDOWN` (only with `CachesData` TRUE) for shutdown and restart, final on
   XP x64 and 7, not final on 2000.
3. **PLAN 0.10 stop path:** "submit a Flush if writes are outstanding" should be "submit a
   Flush if any write completed since the last Flush": on XP x64 and 7 the OS flushes
   nothing before a Device Manager disable, and the writes have already completed when the
   stop arrives.
4. TESTING "Shutdown" and "Orderly stop" cases: the expected trace "Flush after the last
   write, then CC.SHN" holds for disable and hibernate only if the stop path issues the
   Flush itself (point 3); for shutdown/restart the expectation depends on decision 1.
