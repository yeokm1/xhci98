# Gate G6: dump-mode timing and reset

> Prototype source is not on `main`; it stays on the gate branch `phase0-g3g6`: commits
> 4e1e55d (dump mode in `src/g36.c`), ba68658 (fixes found by this gate) and 28ccfe5 (the
> `G6_NOIMPORTS` variant). Shared with [G3.md](G3.md).

PLAN 0.0, G6: does each NT dump port tolerate a synchronous dump-mode `HwInitialize` that
polls up to CAP.TO in short stalls, and which reset requests does it send during dump I/O?
**Pass condition:** crash dump and hibernate complete with RDY delayed by 2 s, and a bus-reset
request during dump I/O is disregarded without failing the dump. **If it fails:** scenario C
(phase 4) is unsupported on that port.

Date: 2026-10-15. usb4-emu `src/qemu/build` (2026-10-15 01:42), TCG, i440FX, SeaBIOS
rel-1.17.0. Also checked: the dump-mode contract of PLAN 4.1/4.2 (dump indication, allocation
under 32 KiB, synchronous init, disregarded reset, completion pump without timers).

## What is testable, and how

- **The dump stack only targets the boot/system disk.** On 2000, XP and 2003-based XP x64 the
  crash dump goes to the paging file on the boot volume and the hibernation file to the
  system volume, both through a copy of the **boot disk's** miniport (`dump_<name>.sys` under
  `diskdump.sys`). With nvme98 driving a data disk (scenario A) its dump path is never
  loaded. Measured on 2000: booted from IDE with the nvme98 disk mounted, CrashOnCtrlScroll
  gave STOP 0xE2, "Physical memory dump complete" (written by `atapi`'s dump stack), and
  nvme98 logged nothing in dump mode (`shots/g6a-bsod.png`). Scenario A's hibernate path
  (power stop and lazy restart) was covered by G7/G8.
- **Scenario C therefore needs scenario B (boot from the NVMe).** In usb4-emu that works:
  with `x-force-tunnel=on` the endpoint is present at POST, **SeaBIOS's NVMe driver hooks it
  into INT 13h** (it leaves CC.EN=1, as G1 saw), NTLDR loads the kernel and the boot drivers
  from it, and nvme98 as a boot-start driver (`Start=0`, group `SCSI miniport`,
  `CriticalDeviceDatabase` entries for `pci#ven_1b36&dev_0010`) finds the boot disk: the
  G1 deferred bring-up first disables the controller SeaBIOS left enabled, then runs as at any
  start (`logs/dcon-w2k-g6c1.log` from line 1). Both **Windows 2000 SP4 and XP x64 SP2 boot
  and run from the tunnelled NVMe** with no IDE disk attached.
- Setup: the 2000 and XP x64 system disks (overlays of the G2/G4 images) were given to the NVMe
  as its backing image; `CrashDumpEnabled=2` (kernel dump), `AutoReboot=0`,
  `i8042prt\Parameters\CrashOnCtrlScroll=1`, hibernation enabled. Crash: QMP key events (right
  Ctrl held, Scroll Lock twice), STOP 0xE2. Hibernate: Shut Down dialog (2000), `rundll32
  powrprof.dll,SetSuspendState` (XP x64). Resume: the same QEMU command line.
- Stimuli: `x-rdy-set-delay-ms=2000` set on the bridge just before the crash or hibernate (so
  it acts on the dump instance's CC.EN); `x-faults` holding (10 s, 90 s) or dropping a write
  completion after the dump had started.
- Windows 7 x64 (q35, test-signed boot driver) was not run.

## Measured dump-port behaviour

Same on 2000 and XP x64 unless stated. Excerpts: [evidence/g6-dump-excerpts.txt](evidence/g6-dump-excerpts.txt).

| Item | Measured |
|---|---|
| Dump indication | Both, every time, crash and hibernate: `DriverEntry(NULL, NULL)` (stage A0 = 0x83) and `HwFindAdapter` `ArgumentString` = `"dump=1;"` exactly (A1). The dump instance is a fresh image copy with fresh statics |
| When | Crash: at the bugcheck. Hibernate: after the runtime instance's `ScsiStopAdapter` (stop path ran, CSTS 0), then the dump instance loads; so hibernate init starts from a disabled controller, crash init from an enabled one (CSTS.RDY=1, queues of the dead runtime) |
| `ConfigInfo` access range | Supplied by the port (BAR0 0xFE800000, 16 KiB). The inherited BAR-sizing dance (write 0xFFFFFFFF, read back) does not work in dump mode: the read-back gives the BAR value itself, so the computed length is 24 MiB and `ScsiPortGetDeviceBase` returns NULL. **Fix:** use the range the port supplies (the prototype retries with it, AA=3) |
| Uncached extension | 28 KiB granted; **64 KiB returns NULL on 2000** (`G6_DUMP_BIG` build: A2 = 0x80010000, `HwFindAdapter` fails, no dump). The 28 KiB block's **physical base is not page aligned** (…020 on 2000): the base allocator aligned offsets, not physical addresses, so ASQ was misaligned and QEMU's controller refused to start (CFS). **Fix:** align against the physical address (PLAN 0.5) and leave a page of slack |
| Synchronous init | Disable (crash only) - RDY=0 - enable - RDY - create CQ/SQ - identify controller and namespace, all inside `HwInitialize` in 100 µs stalls (no timer call issued): 40-60 ms normally, 2.39-2.58 s with RDY delayed 2 s (stall-count time; TCG). No timeout from the dump port during it |
| Requests | INQUIRY, then a **bus reset** (`HwResetBus`, once, right after the INQUIRY, before any media I/O), START STOP UNIT, READ CAPACITY, one READ, then 4 KiB WRITEs one at a time (6,336 for a 256 MB 2000 kernel dump), then SYNCHRONIZE CACHE and `SRB_FUNCTION_SHUTDOWN` at the end of both crash and hibernate |
| Completion pump | The dump port polls `HwInterrupt`: 13-60 polls per write typically. No timer callback ran in dump mode (stage A8 never seen; the prototype never requests one) |
| Reset during I/O | 2000: with a write completion held, one `HwResetBus` 7.7-15 s after the hold (outstanding untagged = 1). Disregarded (TRUE, no controller reset, nothing completed); the port then waited for the held completion (90 s) and the dump completed. With the completion dropped it waited indefinitely (dump stuck at 3 %, 240 s observed). XP x64: no reset at all in 90 s of hold; dump completed after the release |
| Service name | XP x64's dump loader derives the dump image from the **service (driver object) name**: service `nvme2k` with `ImagePath` `NVMe2Kx64.sys` failed with event 45 ("could not load the crash dump driver"), event 49, and hibernate error 0xC0000034 (`STATUS_OBJECT_NAME_NOT_FOUND`). With a copy named `nvme2k.sys` both work. 2000 had matching names. Imports were not the cause: XP x64's `diskdump.sys` exports every `ScsiPort*` routine nvme98 imports, and the build with the G3 `ntoskrnl` callback imports dumps fine |

## Dump-mode contract (PLAN 4.1, 4.2): what passed

| Contract item | Result |
|---|---|
| NULL `DriverEntry` indication and `ArgumentString` "dump" in `HwFindAdapter` | both present (2000, XP x64; crash and hibernate) |
| Allocation under 32 KiB on XP and earlier | 28 KiB works, 64 KiB fails (2000); the budget must include physical-alignment slack |
| Synchronous init within limits | yes, polling to CAP.TO in 100 µs stalls, RDY 2 s tolerated |
| Disable the controller left by the runtime driver first | needed on crash (CSTS.RDY=1 at entry), not on hibernate (runtime stop already disabled it) |
| Bus reset disregarded | yes; the port's single start-of-dump reset and the mid-dump reset (2000) were disregarded without failing the dump |
| Completion pump without timers | `HwInterrupt` polled by the port; worked; **but** nothing ends a command that never completes |

## Consequences

1. **Scenario C is feasible on 2000 and XP x64** with a firmware that boots the NVMe; phase 4
   is not blocked on these ports.
2. **PLAN 4.2's pump deadline is mandatory, not optional.** Neither dump port times out a
   dump write on its own (2000: one reset and then an indefinite wait; XP x64: nothing in 90 s).
   With "disregard the reset", a lost completion hangs the machine at the bugcheck screen,
   and with `AutoReboot` it never reboots. The dump-mode engine needs its own deadline
   (counted in polls or stall time inside `HwInterrupt`/`HwStartIo`) that completes the SRB
   with an error so that the dump fails cleanly.
3. **PLAN 4.1 additions:** use the access range from `ConfigInfo` in dump mode (never size the
   BAR there); keep the dump allocation under 32 KiB *including* physical-alignment slack;
   align every queue and PRP page against the physical address (also PLAN 0.5).
4. **Packaging (phase 6):** the NT service name must equal the image base name (`nvme98` /
   `nvme98.sys`) on every NT target, or XP x64 (and probably 2003-based systems generally)
   cannot load the dump or hibernation driver. The upstream nvme2k x64 INF pairing (`nvme2k`
   service, `NVMe2Kx64.sys`) has exactly this defect.
5. MD-3 option (b) (driver-owned pool) must keep the dump route separate, as R6-2 says: the
   dump instance cannot call the memory manager, and it got only the 28 KiB uncached
   extension.
6. G3 interface 2 must stay off in dump mode (the prototype skips `ExCreateCallback` when
   `DumpMode`); its imports did not disturb the dump driver load.

## Not covered

- Windows 7 x64 (crashdmp.sys + diskdump, test-signed boot driver), Vista, XP x86, 7 x86.
- A dump-mode `HwInitialize` whose RDY wait exceeds CAP.TO (bring-up failure path in dump
  mode: measured only by accident before the fixes, where `HwInitialize` returned FALSE and the
  dump was skipped cleanly: "Beginning dump" never printed, no hang).
- Crash with RDY delayed on XP x64; hibernate with a held completion.
- 4 KiB namespaces in dump mode (PLAN 4.3).
- Real firmware: whether the P14s CSM (or any UEFI) boots a Thunderbolt-attached NVMe at all
  is outside this gate.
