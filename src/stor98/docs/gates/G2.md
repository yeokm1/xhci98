# G2: gone-state hold and the MD-1 deadline

> Prototype source is not on `main`; it stays on the gate branch. Branch `phase0-g2g4`: commits 316bd25 (debug-port layer), 46a4c4e (gone state, MD-1 deadline, truthful `HwResetBus`, `src/g24.c`) and 006edef (`tests/gio` rescan tool). Shared with [G4.md](G4.md); timelines in [evidence/](evidence/).
>
> Windows 7 x64 run (pass): [Q-NT.md](Q-NT.md), item 1.

Gate G2 of [PLAN.md](../PLAN.md) 0.0 asks what each SCSI port does while the miniport holds SRBs
in `gone`, up to and beyond the gone deadline (0.10). Does the port's own SRB timeout fire? Does
it then call `HwResetBus` (G4)? Does it retire the held SRBs itself before the OS removal path?

Pass condition: the behaviour is measured and recorded per port, with the tunnel gate closed and
no G3 notification. The port never completes a held SRB before the OS has itself established
removal.

The brief also asked whether the MD-1 deadline completion ends the XP x64 retry loop (event 117
then 9 every 15 s, usb4-emu `vms/winxp64/RESULTS-winxp64.md`). It asked how long T3 and T4 take,
whether pending SRBs stay bounded, and whether a later tunnel up plus rescan brings the disk
back.

Date: 2026-10-15. Branch `phase0-g2g4`. Prototype commit `46a4c4e`.

## Prototype

`src/g24.c` is a throwaway prototype, not product code. It hooks into the base driver at five points:

- **Presence loss.** An all-ones CSTS read enters `gone`. The read comes from the fallback timer
  (100 ms tick) while SRBs are issued, from `HwStartIo`, or from `HwResetBus`. Issued SRBs, which
  are tracked by queue tag, stay held. New EXECUTE_SCSI, FLUSH and SHUTDOWN SRBs fast-fail with
  the terminal status.
- **Gone deadline (MD-1).** The deadline is `gone=<ms>` (default 5000, 0 = never), counted in
  timer ticks from entering `gone`. At the deadline, each held SRB that the port still lists
  (`ScsiPortGetSrb` returns the same pointer) completes with the terminal status: `st=nodev`
  gives `SRB_STATUS_NO_DEVICE`, `st=seltmo` gives `SRB_STATUS_SELECTION_TIMEOUT`.
  `DataTransferLength` is 0 and `ScsiStatus` is GOOD. PRP list pages stay allocated as quarantine
  (the debug line shows the bitmap), and nothing is reused. `BusChangeDetected` follows (`bcd=1`).
  A held SRB that the port no longer lists would be logged as port-retired and left untouched.
  No such SRB occurred.
- **Port behaviour while holding.** Every second the timer logs held versus port-owned SRBs
  (`ScsiPortGetSrb`). Every `HwResetBus` call and its return value are logged ([G4.md](G4.md)).
- Options come from `DriverParameter` (`ArgumentString`). Stage codes 0x80-0x8E are in
  `src/dbgport.h`.

Guest tools are in `tests/gio`. `gio.exe` issues unbuffered, overlapped, write-through I/O on
`\\.\PhysicalDrive2` at QD 8 with 64 KiB requests. Reads were used on XP x64 because its disk
carries a mounted NTFS volume. A read/write mix was used on Windows 2000 in a raw partition. gio
prints the first error (T3) and the moment the disk can no longer be opened (T4, probed every
1 s), with TSC stamps. `rescan.exe` does "Scan for hardware changes" through
`CM_Reenumerate_DevNode`.

  `run-w2k.sh` (QMP 48090) and `run-xp.sh` (QMP 48092). The device lines are those of

  `isa-debugcon`. Traces: `usb4_dbg_*`, `usb4_h_*`, `usb4_tp_*` and `pci_nvme_*`.

  `winxp64.qcow2`. The NVMe images are overlays on `win2k/nvme8g-base.qcow2` and
  `winxp64/nvme4g.qcow2`. Every run started from fresh disposable overlays. No base image was
  modified.
- The test build (`NVME98_DBGPORT=1`, `out/free-dbgport/{x86,amd64}/nvme98.sys`) was copied over
  the installed nvme2k service image (`nvme2k.sys`, `NVMe2Kx64.sys`). The service name, INF and
  registry are unchanged. `DriverParameter` was set under `Services\<svc>\Parameters\Device`.
  Each option change used a fresh adapter instance (tunnel down, rescan, tunnel up, rescan).
- Stimulus: the harness held the 3000th to 3007th I/O commands at fetch, then the 3007th fetch
  took the tunnel down (`act=surprise`), so the miniport held exactly 8 SRBs at T0. Run W2K-A
  used a plain QMP `tunnel surprise` during reads instead. The "no evidence" case used
  `act=reads-fail` (MMIO all-ones, DMA alias open, endpoint not reset) instead of `surprise`.
- T0 is the `usb4_tp_gate closed=1` trace event. T1 is `GONE_ENTER`. T2 is `DEADLINE` (the last
  `HELD_DONE`). T3 is gio's first error. T4 is gio's first failed open of the PhysicalDrive.
  Guest TSC is converted to trace time through `usb4_dbg_marker` samples (`g24log.py --tsc`).
  All times below are host-clock ms after T0.

### Against the TESTING.md thresholds (MD-1 runs)

- **T0 to T1:** 1.5 to 108 ms. Limit 2 s.
- **T1 to T2:** 5.0 to 5.6 s, except two Windows 2000 runs at 7.8 s (W2K-A and W2K-B).
  - The deadline is 50 timer ticks. Under TCG with QD 8 load, the Windows 2000 guest clock ran
    slow: gio's `GetTickCount` advanced 5.02 s while the TSC advanced 7.83 s. The deadline
    therefore ended on time in guest time.
  - This does not meet "5 s after T1 ±1 tick" in host time. The product build should take the
    deadline from a clock it can trust, not from a callback count (see PLAN changes).
- **T0 to T3:** at most 8.0 s. Limit 60 s.
- **T4:** at most T0 + 8.0 s. Limit T0 + 60 s.
- **Recovery events:** 0 bus resets and 0 timeouts in the window, on both OSes.
- **Driver-pending SRBs:** never above 8, the application QD. Nothing else was pending in the
  miniport.
- The 10-minute sustained-absence window was not run end to end. After T4 no further SRB
  reached the miniport; the only one was a single INQUIRY at most 1 s later.

## Answers

1. **Does the port's own SRB timeout fire while SRBs are held?** Yes, once the disk timeout
   expires. That took 16.1 s host time (about 10 s guest) on 2000 and 11.1 s on XP x64. With the
   5 s MD-1 deadline it never fires, because the deadline comes first.
2. **Does it then call `HwResetBus`?** Yes, once. It does nothing else while the SRB stays held:
   no second reset, no forced completion, no removal, for 5 to 7 min (see G4.md for the variants).
3. **Does the port retire held SRBs itself before the OS removal path?** No, on either port. It
   retires them (as "no such device") only when PnP removes the controller after a rescan. That
   is removal the OS has established, as the pass condition allows.
4. **Does the MD-1 completion end the XP-style retry loop?** Yes. With NO_DEVICE or
   SELECTION_TIMEOUT the class driver does not retry. The application gets its error at T2, the
   disk is gone within milliseconds (`BusChangeDetected`), and no 117 or 9 event appears.
   - The 117/9 loop seen with nvme2k needs a `HwResetBus` that returns TRUE and completes
     everything with `SRB_STATUS_BUS_RESET`, which the class driver retries. The prototype's
     truthful FALSE does not start the loop even without a deadline. It produces a single reset
     and a hang, as in W2K-D and XP-D, and that hang is what MD-1 exists to end.
5. **Does a later tunnel up plus rescan bring the disk back?** Yes, through PnP:
   - Without a hot-plug driver, a rescan with the tunnel down first removes the controller.
   - Tunnel up plus rescan then starts a fresh adapter instance.
   - The old instance stays in `gone` until PnP removes it. The prototype does not re-initialise
     in place.
6. **NO_DEVICE versus SELECTION_TIMEOUT.** Both end the retries.
   - NO_DEVICE reaches the application as `ERROR_FILE_NOT_FOUND` (2) and logs nothing.
   - SELECTION_TIMEOUT reaches it as `ERROR_DEVICE_NOT_CONNECTED` (1167). It logs Disk event 15
     three times on XP x64; Windows 2000's log was not checked.
   - Either is acceptable for 2.2. NO_DEVICE stays the default.

## Observations for other gates and items

- **No stop callback on surprise removal.** On both ports PnP surprise removal of the controller
  (rescan with the tunnel down) produced no `HwAdapterControl(ScsiStopAdapter)` at all, with or
  without held SRBs. The miniport timer stopped (no further ticks in the trace). This bears on
  PLAN 0.11's "stop with device already absent" row and on G5.
- **Leftover adapter instance.** In two cycles a rescan right after a tunnel down did not remove
  the controller. In at least one of them the rescan command never ran, because Ctrl-C was sent
  on the wrong key (US-Dvorak). A later rescan removed it. The tunnel-up rescan then found the
  old instance still present on the new endpoint.
  - xhci98's CM (REENUM-EXPERIMENT) must make sure the controller devnode is removed before it
    raises the tunnel again.
- **`BusChangeDetected` is only a disk-level removal.** At the deadline it makes the port rescan,
  the INQUIRY fails with the terminal status, and the disk PDO is surprise-removed within 2 to
  25 ms. Controller removal still needs PnP (a rescan, or the CM).

## Consequence and PLAN changes

G2 passes on Windows 2000 and XP x64, so the held-SRB design of `gone` (0.10) and the MD-1
deadline are safe on these ports. Proposed PLAN updates (for the maintainer; not applied here):

- **Record G2:** pass on 2000 and XP x64; not run on 98/ME (G9 territory), XP x86, Vista or 7.
- **Notify `BusChangeDetected` at the gone-deadline outcome.** 2.2 already asks for one per
  transition. It is what makes T4 fast (milliseconds) on both ports without a rescan.
- **Gone deadline below the disk timeout.** Keep the deadline below the class/port SRB timeout
  (TimeOutValue, about 10 s here) minus detection time. Then the port never resets during
  `gone`. If it does, the outcome is still safe: one FALSE reset and then a hang (G4).
- **Gone deadline from elapsed time, not tick counts.** Measure the deadline (and the watchdog
  deadlines of 2.3) as elapsed time. Timer callbacks were delayed by up to 55% under load: 50
  ticks of 100 ms took 7.8 s.
- **Terminal status.** Keep `SRB_STATUS_NO_DEVICE`. `SRB_STATUS_SELECTION_TIMEOUT` is
  equivalent for retries; it differs in the Win32 error (1167 instead of 2) and in the Disk
  event 15 entries.
- **0.11 matrix.** On surprise removal (2000, XP x64) no `ScsiStopAdapter` arrives. Held SRBs are
  retired by the port, and the miniport gets no callback. Record this in the "stop with device
  already absent" row.
