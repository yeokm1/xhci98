# G4: port behaviour after a failed reset

> Prototype source is not on `main`; it stays on the gate branch. Branch `phase0-g2g4`: commits 316bd25 (debug-port layer), 46a4c4e (prototype) and 006edef (`tests/gio`), as for [G2.md](G2.md).
>
> Windows 7 x64 run (pass for the failed disable; stuck controller not run): [Q-NT.md](Q-NT.md), item 1.

Gate G4 of [PLAN.md](../PLAN.md) 0.0 asks what each port does when `HwResetBus` returns FALSE,
or returns while the miniport still holds SRBs. Does it complete them itself, call the reset
again, or start removal?

Pass condition: the behaviour is measured and recorded per port. The port never completes a held
SRB while the device may still reach its buffer; a forced completion is allowed only after the OS
has itself established removal. If it fails, the held-SRB design of the unresponsive row is not
safe on that port, and the port is blocked pending a maintainer decision.

Date: 2026-10-15. Branch `phase0-g2g4`. Prototype commit `46a4c4e` (`src/g24.c`). The setup,
tools, images and time base are as in [G2.md](G2.md).

## Results

| OS | Verdict | What the port does after `HwResetBus` returns FALSE |
|---|---|---|
| Windows 2000 SP4 | **Pass** | No forced completion. One reset per expired timeout: a second call came only after another full timeout, 23 s later, and only when other requests had completed in between. Otherwise there was one call in 3 to 5 min. No removal, no bugcheck. The LU queue stalls: no new SRBs reach the miniport and the application blocks without an error. The port accepts a later miniport completion of the held SRBs (normal, BUS_RESET plus `ResetDetected`, or the MD-1 terminal status) and resumes. It retires held SRBs itself only on PnP removal. |
| Windows XP x64 SP2 | **Pass** | Same. The second call came 15 s after the first. No event 9 or 117 was logged in any run. |
| Windows 7 x64 | Not run | Skipped for time. |

No consequence applies on either port. The truthful-return rule of 0.10 (TRUE only on an
acknowledged disable, otherwise FALSE with the SRBs still owned) is safe on 2000 and XP x64.

## Prototype

`HwResetBus` in `src/g24.c`:

- **In `gone`, or when CSTS reads all-ones:** returns FALSE with no waits.
- **Otherwise:** writes CC.EN=0 and polls CSTS 10 times, 100 µs apart (the stall budget).
  - If RDY reads 0 from a CSTS value that is not all-ones, the held SRBs complete with
    `SRB_STATUS_BUS_RESET` and it returns TRUE. The prototype then stays `failed`: it does not
    re-create queues.
  - Otherwise it returns FALSE, the SRBs stay held, and the state is `RESET_WAIT`. New SRBs then
    fail with HARDWARE ERROR 04/44/00.
- **In `RESET_WAIT`, each 100 ms tick:**
  - RDY=0 with CC.EN=0: completes the held SRBs with BUS_RESET and notifies `ResetDetected`.
  - All-ones: enters `gone`, and the MD-1 deadline applies.
- **`reset=legacy`** restores the base behaviour (complete everything, return TRUE). It was not
  needed.

Every call is logged with the number of SRBs held and still listed by the port
(`ScsiPortGetSrb`). Its result, the CSTS byte and the later outcome are logged too.

## Evidence

The trimmed timelines are [evidence/g24-w2k-s1-timeline.txt](evidence/g24-w2k-s1-timeline.txt)
and [evidence/g24-xp-x1-timeline.txt](evidence/g24-xp-x1-timeline.txt). The full traces and
screenshots are in usb4-emu `vms/nvme98-g24/{logs,shots}` (local). Times are host ms from the
fault.

### Windows 2000

**Gone, held forever (`gone=0`, run W2K-D in G2.md).**
- Setup: 8 SRBs held after a surprise removal.
- Port: `HwResetBus` #1 at T0+16.1 s, state GONE, FALSE, 8/8 still listed by the port. Nothing
  else for 5 min: no second reset, no completion, application blocked.
- End: a rescan removed the controller, and the port then completed the 8 SRBs itself (error 2).

**Stuck controller (`x-hang=stuck` during QD 8 mixed I/O).**
- Setup: CSTS frozen at RDY=1, BAR writes dropped, 8 held.
- Port: `HwResetBus` #1 11 to 14 s after the hang (the hang took effect between two 1 s samples). CSTS reads 0x01, CC.EN=0 is written but
  dropped, so the result is FALSE and the state RESET_WAIT. No second reset in 3.3 min; 8/8
  listed by the port.
- After `x-hang=off`, the controller completed the 8 held commands:
  - The port accepted the miniport's normal completions (gio `ok` +8).
  - The next 8 SRBs reached the miniport and failed with HARDWARE ERROR (one class retry each).
  - The application got error 1117. Bounded; no reset loop.

**Failed disable (`x-rdy-clear-delay-ms=-1`, one completion held: `at=complete nth=3000 act=hold`).**
- Port: `HwResetBus` #1 10.7 s after the hold. CC.EN=0 resets the controller (the held command is
  discarded) but RDY keeps reading 1, so the result is FALSE and the state RESET_WAIT. One
  queued WRITE then failed with HARDWARE ERROR and was retried by the class driver.
- Port: `HwResetBus` #2 23.4 s after #1, FALSE. Then nothing for 3.7 min. The other 7 requests
  were never dispatched to the miniport, and the application blocked with no error.
- Then `x-rdy-clear-delay-ms=0` let the watchdog see RDY=0 with CC.EN=0:
  - The held SRB completed with BUS_RESET and `ResetDetected` was notified.
  - About 3 s later the port dispatched the stalled requests. They failed with HARDWARE ERROR
    because the prototype stays `failed`, and the application got error 1117 for all 8.

**Healthy controller, held completion (incidental run).**
- Cause: the hold rule stayed armed into the next adapter's bring-up and held its first READ.
- `HwResetBus` came 17.1 s later. The disable was acknowledged inside the 1 ms budget, so the
  held SRB completed with BUS_RESET first and the call returned TRUE.
- The port went on normally. Later I/O failed only because the prototype does not re-create
  queues.

**`HwResetBus` while gone, from the timeout of a still-held SRB.** This is the same call as in
the gone case above: FALSE, no waits, and the port did nothing more.

### Windows XP x64

**Gone, held forever (XP-D).** `HwResetBus` #1 at T0+11.1 s, FALSE. Nothing more for 7 min; no
9 or 117 event. A rescan made the port complete the held SRBs (error 2).

**Stuck controller.**
- Port: `HwResetBus` #1 12 s after the hang, CSTS 0x01, FALSE, RESET_WAIT. Nothing more for
  4.6 min.
- On `x-hang=off` the controller had nothing to run. The SQ doorbells written during the hang
  had been dropped, so the 8 commands were never fetched and the SRBs stayed held.
- A later surprise removal moved RESET_WAIT to `gone`, and the 5 s deadline completed the 8 SRBs
  with NO_DEVICE. The port accepted them; the disk was removed.

**Failed disable with a held completion.**
- Port: `HwResetBus` #1 10.0 s after the hold, FALSE. One queued READ failed with HARDWARE
  ERROR. `HwResetBus` #2 15.3 s later, FALSE. Then nothing for 3 min; the application blocked.
- A late acknowledgement (`x-rdy-clear-delay-ms=0`) completed the held SRB with BUS_RESET plus
  `ResetDetected`. About 3.3 s later the stalled SRBs were dispatched and failed with HARDWARE
  ERROR, and the application got error 1117.
- Event log: Disk event 11 for each HARDWARE ERROR completion. No event 9 or 117. The only
  9/117 entries in the log are from the nvme2k evaluation on 2026-10-14.

## Answers

1. **Does the port complete held SRBs itself after FALSE?** No, on either port. The only
   port-side completion seen was after PnP removal of the controller (G2).
2. **Does it call the reset again?** Only when another full timeout elapses and requests have
   completed in between, as in the failed-disable runs (#2 after 23 s on 2000, 15 s on XP x64).
   With nothing completing (stuck or gone) there is one call, then none for 3 to 7 min. There
   was no tight loop.
3. **Does it start removal?** No. Removal came only from PnP (rescan).
4. **Does it bugcheck?** No.
5. **What happens to new requests after FALSE?** The port stops dispatching to the LU. At most
   one SRB reached the miniport between the two resets. The volume hangs and the application
   sees no error until the miniport completes or acknowledges.
   - This is the outcome the PLAN's unresponsive row accepts.
   - That row's "new SRBs fast-fail" is not reached in practice: the port holds them back
     instead.
6. **Does a late acknowledgement work?** Yes. Completing the held SRBs with BUS_RESET and
   notifying `ResetDetected` from the timer is accepted. The port resumes dispatch about 3 s
   later, and no double completion was seen.

## Consequence and PLAN changes

G4 passes on Windows 2000 and XP x64. The unresponsive and presence-lost rows of 0.10 can rely
on the port not completing held SRBs after a FALSE return. Proposed PLAN updates (not applied):

- **Record G4:** pass on 2000 and XP x64; Windows 7 x64, Vista, XP x86 and 9x not run.
- **Unresponsive row.** After FALSE the port withholds further SRBs, so the volume hangs without
  application errors until acknowledgement, removal or the MD-1 deadline (presence lost).
  "New SRBs fast-fail" applies only to the few already dispatched. State this in 0.10 and in
  TESTING "Failed disable": "no repeated controller resets" holds as "at most one reset per
  expired port timeout".
- **Watchdog recovery.** When a disable is acknowledged after `HwResetBus` returned FALSE, notify
  `ResetDetected` after completing the held SRBs with BUS_RESET. This is already in the
  entry-points table for driver-initiated resets; the port resumes about 3 s later.
- **TESTING "Failed disable".** Add the measured port behaviour:
  - one `HwResetBus` per expired timeout, about 10 s apart, 15 to 23 s when requests complete in
    between;
  - LU dispatch stalled;
  - no 9 or 117 events on XP x64;
  - a late completion of the held SRBs is accepted.
