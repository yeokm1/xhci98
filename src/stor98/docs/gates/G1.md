# Gate G1: deferred bring-up

> Prototype source is not on `main`; it stays on the gate branch. Branch `phase0-g1g8`: commits 316bd25 (debug-port layer, `src/dbgport.{c,h}`) and 759d860 (deferred bring-up and shutdown-path markers). Shared with [G8.md](G8.md).

PLAN 0.0, G1: can `HwInitialize` (and the resume path) set CC.EN, return TRUE and finish
bring-up from the timer, holding requests or returning BUSY until it is ready?

**Pass condition:** on each port, with RDY delayed well past the callback budget and,
separately, with identify failing, the bus scan completes (disk present, or no disk), no SRB
times out into a port reset during bring-up, and a failed bring-up ends in state `failed`
with the adapter started and its memory still owned.

Date: 2026-10-14/15. Prototype: branch `phase0-g1g8`, commits 316bd25 (debug port layer)
and 759d860 (prototype; hybrid request policy as the default).

| Windows 7 x64 SP1 (q35, TCG) | disk present, no reset (hold; hybrid threshold not reached) | `failed`, no disk, adapter started | `failed`, no disk, adapter started | `ScsiRestartAdapter` -> deferred, OK | **PASS** |

| XP x86, Vista, 7 x86 | not run (no VM in this session) | | | | open |

Consequence: none of the three tested ports needs the G1-failure fallback (synchronous
bring-up in `HwFindAdapter`). The deferred model of PLAN 0.10 holds on 2000, XP x64 and 7 x64
**provided requests are not held past the SRB's own timeout**: holding is safe only for a
bounded time, after which the request must be completed BUSY (hybrid policy). Pure hold is
not safe on Windows 2000, whose bus-scan INQUIRY carries a 4 s timeout.

## The prototype (what was tested)

- `HwInitialize`: reads CSTS; all-ones returns FALSE (CC.EN never written); masks INTMS;
  reads CAP/VS; CFS with CC.EN=0 returns FALSE; carves the queues from the uncached
  extension **once** (a restart reuses them); if a previous owner left CC.EN=1 or RDY=1
  (SeaBIOS does, whenever the NVMe is present at POST) it writes CC.EN=0 and lets the timer
  wait for RDY=0 (state `DISABLING`); otherwise programs AQA/ASQ/ACQ and writes CC.EN=1
  (state `WAIT_RDY`). Then `RequestTimerCall(BringupTimer, 10 ms)` and returns TRUE.
- `BringupTimer`: one step per tick, no stall loops: RDY within CAP.TO, then the admin chain
  (create I/O CQ, create I/O SQ, identify controller, identify namespace) polled from the
  admin CQ, then `RUNNING` (INTMC unmasks vector 0, fallback timer enabled). Failure after
  CC.EN: write CC.EN=0, wait for RDY=0 within CAP.TO -> `FAILED`, else `QUARANTINED`
  (rechecked once a second; an acknowledged disable later moves it to `FAILED`).
  All-ones CSTS at any step -> `QUARANTINED` without waits.
- Requests in a starting state: the first SRB is held (no `NextRequest`, so the port sends
  nothing else); the timer dispatches it through `HwStartIo` once `RUNNING`, or completes it
  in a failed state (INQUIRY -> `SRB_STATUS_SELECTION_TIMEOUT` when identify never
  succeeded, so no disk is created; other CDBs -> `ERROR` with sense 04/44/00; flush and
  shutdown -> SUCCESS). `HwResetBus` forgets a held SRB (the port completes it).
- INTx is enabled in the PCI command register by `HwFindAdapter` after INTMS is masked;
  `HwInitialize` no longer touches config space (PLAN 3.4).
- Test options from the registry `DriverParameter` (Parameters\Device): `g1=hold`,
  `g1=busy`, `g1=hybrid` (default after this gate).

Stage codes and their meaning: `src/dbgport.h`. Decoder: usb4-emu
`vms/nvme98-g18/stages.py` (local).

## Measured port behaviour

### Timer from `HwInitialize`

`ScsiPortNotification(RequestTimerCall)` from `HwInitialize` works on all three ports: the
first `BringupTimer` call follows the `HwInitialize` return by 5-25 ms (stage 0x47). The tick
is coarser than requested: 10 ms asked, about 15.6 ms delivered on 2000 at run time and
on XP x64 (130 ticks for 2.04 s; 250 ticks for 4.0 s), 10 ms on 2000 at boot and after
resume. Deadlines counted in ticks therefore run long (CAP.TO 7.5 s became 11.8 s on 2000 and
XP x64, 12.0 s on 7). That errs on the safe side for RDY waits; product code needs a
wall-clock base or must document it.

### What arrives during bring-up

On every port the first request after `HwInitialize` is the bus-scan INQUIRY (or START STOP
UNIT on resume), and **its `TimeOutValue` is what bounds a hold**:

| Port | First SRB | TimeOutValue |
|---|---|---|
| 2000, start/scan | INQUIRY | **4 s** |
| XP x64, start/scan | INQUIRY | 10 s |
| 7 x64, start/scan | INQUIRY | 60 s |
| 2000, XP x64, 7: `ScsiRestartAdapter` after hibernate | START STOP UNIT | 240 s |

`HwAdapterControl(ScsiQuerySupportedControlTypes)` arrives right after `HwInitialize`
returns, before the first SRB. With the SRB held (no `NextRequest`) nothing else is sent.

### Windows 2000: the pure-hold failure and the BUSY behaviour

Device Manager enable, `x-rdy-set-delay-ms=6000`, `g1=hold` (`logs\w2k-g1-enable-rdy6000-hold.txt`):

```
  57.8 ms  11 SRB_HELD EXEC:INQUIRY st=WAIT_RDY TimeOutValue=4s
5421.2 ms  50 RESET_BUS path=0 held=1 st=WAIT_RDY      <- port timeout -> HwResetBus
6048.9 ms  41 RDY_SEEN
6111.0 ms  43 BRINGUP_DONE
11661.9 ms 10 STARTIO EXEC:INQUIRY st=RUNNING           <- retried after the reset hold
```

The port timed the held INQUIRY out (4 s + its 1 s timer granularity) and reset the bus;
the disk still appeared after the retry, but the gate requires no reset. Same delay with the
hybrid policy (final threshold, a quarter of TimeOutValue;
`logs\w2k-g1-enable-rdy6000-hybrid-final.txt`, screenshot `shots\w2k-g1-final-rdy6000.png`):

```
  58.2 ms  11 SRB_HELD EXEC:INQUIRY TimeOutValue=4s
1050.1 ms  15 HELD_TO_BUSY ticks=100 INQUIRY
1290.9 ms  11 SRB_HELD EXEC:INQUIRY                    <- port re-sent it 240 ms later
2282.3 ms  15 HELD_TO_BUSY ... (5 BUSY cycles, re-sent after 9-240 ms each)
6057.4 ms  41 RDY_SEEN
6097.9 ms  12 DISPATCH_HELD INQUIRY -> RDCAP, reads; no RESET_BUS
```

The port re-issues a BUSY INQUIRY after 9 ms to 1.2 s (both observed). Up to 5 consecutive
BUSY completions of the scan INQUIRY were accepted without the scan failing; the port's
BUSY retry limit was not reached and is not known. With CAP.TO = 7.5 s (QEMU) and a 1 s
hold, at most about 8 BUSY completions can happen before bring-up succeeds or fails.

### RDY never set, identify failing

RDY 20 s (past CAP.TO) on 2000 (`logs\w2k-g1-enable-rdy20000-hybrid-fail.txt`; the same
on XP x64 with -1, `logs\xp-g1-rdynever.txt`, and 7, `logs\w7-g1-rdynever.txt`):

```
   11757.7 ms  44 BRINGUP_FAIL 1 (RDY timeout)   CC.EN=0 written
   11773.6 ms  45 DISABLE_ACK                    RDY=0 read, CSTS not all-ones
   11773.8 ms  40 STATE FAIL_DISABLE -> FAILED
   11774.0 ms  14 SRB_FAILED_STATE EXEC:INQUIRY SrbStatus=0a (SELECTION_TIMEOUT)
```

Identify Controller failing with status 0x6 (`logs\w2k-g1-identify-fail.txt`,
`logs\xp-g1-identify-fail.txt`, `logs\w7-g1-identify-fail.txt`): `ADMIN_DONE cid=3

`SELECTION_TIMEOUT`, all within 60 ms.

In every failure run the scan completed with no NVMe disk, the controller stayed started
in Device Manager with no error code (`shots\w2k-g1-rdytimeout-nodisk.png`,
`shots\w7-g1-rdynever-started.png`, `shots\xp-g1-rdynever.png`,
`shots\xp-g1-identifyfail.png`), and no port reset occurred. The driver frees nothing; the
uncached extension stays the port's allocation for the started adapter. A later Device
Manager disable of a `FAILED` adapter reached `ScsiStopAdapter` with RDY already 0 and did
no waits.

### Resume path (feeds G7)

With `ScsiRestartAdapter` advertised (inherited), resume from hibernation calls
`HwAdapterControl(ScsiRestartAdapter)` -> `HwInitialize`; the deferred bring-up then runs
from the timer exactly as at start, with START STOP UNIT (240 s) held
(`logs\w2k-g8-resume-from-hibernate.txt`, `logs\xp-g8-resume-from-hibernate.txt`,
`logs\w7-g8-resume-from-hibernate.txt`). On 2000 and XP x64 the restart happened only at the
first I/O after resume (lazy disk power-up), not at resume time. Queue addresses after the
Windows 7 resume were the same as before hibernation (allocation preserved over power-down),
while after a Device Manager disable/enable they changed on 2000 and 7 every time and on XP
x64 sometimes (the port may reallocate the uncached extension on a new start): input for
G5/G7.

## Request policy (design selected)

- **Hybrid** becomes the prototype default: hold the first request while starting (no
  `NextRequest`), complete it `SRB_STATUS_BUSY` once a quarter of its `TimeOutValue` has
  passed (counted in nominal ticks, so 1.5-1.6 s real for a 4 s INQUIRY with 15.6 ms
  ticks), and hold the re-sent request again. Never BUSY after a child is issued (none is
  issued while starting).
- Pure hold is unsafe on Windows 2000 when bring-up exceeds 4 s; pure BUSY was not needed
  and not measured.
- The port's BUSY retry limit is unknown: the worst case seen was 5 consecutive BUSY
  completions of the scan INQUIRY without failing the scan. A longer CAP.TO (real SSDs report
  up to 127.5 s) would mean many more BUSY cycles; before product code relies on hybrid for
  long RDY waits, measure the limit (run with `x-rdy-set-delay-ms` close to a raised CAP.TO,
  or `g1=busy`) or lengthen each hold to just under half the TimeOutValue with a wall-clock
  base.
