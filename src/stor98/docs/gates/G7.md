# Gate G7: resume path

> Prototype source is not on `main`; it stays on the gate branch. Branch `phase0-g5g7`: commits 316bd25 (debug-port layer) and b3ae1ef (prototype), as for [G5.md](G5.md).
>
> Windows 7 x64 run (pass) and the resume-failure semantics with the deferred bring-up on 2000, XP x64 and 7 x64 (pass): [Q-NT.md](Q-NT.md), items 1 and 2. With them G7 is a full pass on all three.

PLAN 0.0, G7: with `ScsiRestartAdapter` not advertised, does the port resume through
`HwFindAdapter`/`HwInitialize`, and are allocations preserved?

**Pass condition:** resume works through the normal init path with the failure semantics of
the bring-up rule (0.10).

**If it fails:** advertise `ScsiRestartAdapter` on that port only with measured evidence of
how the port handles each return value; `ScsiAdapterControlUnsuccessful` is never returned
without it.

Date: 2026-10-15. Prototype: branch `phase0-g5g7`, commit b3ae1ef (on 316bd25). Setup,
tools and evidence paths are those of [G5.md](G5.md).

What passes: with `ScsiRestartAdapter` not advertised, both ports resume through the normal
init path and preserve the device extension and the uncached extension across a power
stop, so PLAN 0.5's "reuse allocations across power stop/resume" holds on both. The base's
`ScsiRestartAdapter` path is not needed and the base's `ScsiAdapterControlUnsuccessful`
return is gone.

What is not yet shown: resume **failure** under the bring-up rule. This branch keeps the
base's synchronous `HwInitialize`, so the failure test exercised the forbidden pattern
(FALSE after CC.EN was written), and both ports then hang the I/O: XP x64 never starts an
SRB, 2000 starts one that is never completed, and neither port times out or resets within
four minutes. That confirms the bring-up rule is needed on resume as at boot: `HwInitialize`
must return TRUE and fail into state `failed` with SRBs fast-failed. The deferred bring-up
of G1 (`phase0-g1g8`, 759d860) implements that; the resume-failure case must be rerun with
it and without `ScsiRestartAdapter` (G1 measured its resume path only with
`ScsiRestartAdapter` advertised, the base's setting).

## What was tested

- `HwAdapterControl` (commit b3ae1ef): `ScsiQuerySupportedControlTypes` sets
  `ScsiStopAdapter` and `ScsiSetRunningConfig` only, each checked against
  `MaxControlType`; `ScsiStopAdapter` runs the bounded stop path (G5); `ScsiSetRunningConfig`
  records the PCI command and status registers; anything else returns
  `ScsiAdapterControlUnsuccessful` (never reached in these runs).
- `HwInitialize` restarts the uncached sub-allocator at offset 0 on every call. The base
  never reset it, so a second initialisation without a new `HwFindAdapter` (the base's
  `ScsiRestartAdapter` path) ran out of uncached memory and failed. With the probe, the
  resume `HwFindAdapter` reruns `HwFoundAdapter`, which also resets it.
- Hibernate: XP x64 `powercfg /hibernate on`, `rundll32 powrprof.dll,SetSuspendState`
  (resume password turned off with `powercfg /globalpowerflag off /option:resumepassword`);
  2000 Shut Down dialog, Hibernate. QEMU exits (XP x64) or reaches "safe to turn off"
  (2000, quit from QMP); the same command line with the same overlays then resumes. The NVMe
  is present at power-on (`x-force-tunnel=on`), so SeaBIOS has enabled the controller before
  Windows resumes (`HWINIT_ENTER` sees CSTS.RDY=1); the base `HwInitialize` disables it
  first.
- Resume failure: `x-faults=at=complete op=identify repeat=on act=none status=0x6` set on
  the bridge for the resumed run (XP x64 run h4r, 2000 run h4r). SeaBIOS's identify fails
  too, which only hides the disk from the BIOS.

## Consequence

No `ScsiRestartAdapter` on 2000 and XP x64: the normal init path works and preserves
allocations, so the PLAN 0.11 power row stands with one correction (below). The failure
half of the pass condition is to be rerun on the merged G1 + G7 prototype; until then the
measured fact is that returning FALSE from `HwInitialize` on resume hangs the volume on both
ports, so that return is never used after CC.EN, exactly as 0.10 already says.

## Proposed PLAN changes (not applied here)

- 0.11 power row: the measured callback sequence is `ScsiStopAdapter` at power-down, then at
  the first request after resume `HwFindAdapter` (same device extension, not zeroed) and
  `HwInitialize`. `ScsiSetRunningConfig` was not called on either port although advertised;
  PCI command restoration therefore cannot rely on it and stays in `HwFindAdapter`
  (permitted there, 3.4).
- 0.11 resume row: add the measured result of returning FALSE (both ports hang the I/O,
  2000 still dispatches an SRB to the adapter), as the reason the bring-up rule applies on
  resume.
- 0.5: power stop preserves the uncached extension and the device extension (measured), so
  "reused where G7 shows the port preserves them" applies to power on both ports; the
  per-start reset of the sub-allocator and lifecycle flags is needed (the base lacked it).
- TESTING "Suspend/resume": S3 is not available on these VMs (XP x64: display driver veto
  with std VGA; 2000: `acpi=off`). Hibernate is the tested transition; the 20-cycle soak was
  not run (three cycles on XP x64, two on 2000).
