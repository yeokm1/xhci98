# Gate G9: Windows 9x IOS integration (minimal 0.12)

> Prototype source is not on `main`; it stays on the gate branch. Branch `phase0-g9`: commits 1acd4ad (9x debug-console and debug-port instrumentation, `src/g9dbg.{c,h}`, levels 1-3) and b555ff6 (levels 4-5 for the Windows Me stop investigation). The `NVME98_G9` build switch under "Reproduction" exists only on that branch. Evidence in [G9/](G9/).

Run 2026-10-14/15 on Windows 98 SE in usb4-emu, and on 2026-10-15 on Windows Me (section
"Windows Me"). Gate definition: [PLAN.md](../PLAN.md) 0.0
(G9), 0.12, 2.7, 3.4. The question: is the stock IOS and Configuration Manager (CONFIGMG)
path enough for nvme98's lifecycle on Windows 9x, or does nvme98 need a helper VxD?

## Verdict

**98 SE: pass. The stock path is enough, so no helper VxD is needed. NVMEVSD.VXD is not
needed either. Windows Me: blocked pending a maintainer decision, because Me's port gives
the miniport no stop or shutdown callback (below).**
On 98 SE, IOS, CONFIGMG and the 9x SCSI port layer (SCSIPORT.PDR) handle arrival, orderly
removal, volume dismount and re-arrival with the plain `.mpd`. After a surprise removal,
IOS gives up cleanly and reports an error to the application with no hang. This works
only if the miniport completes the requests with an error status. The base driver holds
them or returns BUSY, and then the request hangs.

Two findings constrain the design. Neither needs a helper VxD:

1. **The `.mpd` is unloaded at every removal.** The port calls `HwAdapterState(FALSE)` as
   the only stop callback. It then unloads the image and frees the device extension and
   the uncached extension. The next arrival runs `DriverEntry` with fresh static data. A
   timer armed in that callback never fires. Driver-owned DMA memory that must stay
   quarantined (MD-1) therefore cannot live in the port's uncached extension on 9x (G5,
   below).
2. **Nothing removes the volume after a surprise removal except CONFIGMG.** IOS keeps the
   DCB and the drive letter, and serves cached directory listings, until something calls
   `Remove_SubTree` or `Reenumerate_DevNode` on the devnode. That caller is xhci98's CM
   (usb4-emu `REENUM-EXPERIMENT.md`, mechanism B) or the user (Device Manager Refresh or
   Remove). The miniport's part is to fail requests quickly.

**Windows Me (run 2026-10-15): blocked pending a maintainer decision.** The stock path
handles arrival, volume dismount, re-arrival and the end of I/O after a surprise removal
exactly as on 98 SE. But Me's SCSIPORT.PDR never calls a stop. `HwAdapterState(FALSE)`
did not come at a CONFIGMG remove, a Device Manager Remove or system shutdown. The port
unloads the image and frees its memory while the controller is still enabled, and Me
powers off without shutting the controller down. On Me this fails G5 (even for an
orderly removal) and leaves G8 without a final trigger. The options are in "Windows Me"
below. A follow-up investigation ("Windows Me stop investigation") found the cause in Me's
IOS, not its port. The three SCSIPORT.PDR builds handle the same events in the same way.
Me's IOS never sends `AEP_SYSTEM_CRIT_SHUTDOWN`. It also no longer sets the DDB flag on
which the port's removal stop depends; on 98 SE that flag is set only because two IOS
flags share a value. Setting `CachesData = TRUE` gives Me an `SRB_FUNCTION_SHUTDOWN` at
shutdown (measured). A removal stop on Me needs either a helper VxD or an undocumented
DDB flag write by the miniport (measured as an experiment).

## Results by scenario

### Arrival: tunnel up after boot, then CONFIGMG re-enumerate (runs a, b, c)

Without NVMEVSD.VXD, IOS loads the miniport, creates the DCB and mounts the volume as F:
(`a1-arrival-dir.png`). The call order is the same in every load (`debugcon-a.log`
seq 0-70):

```
DriverEntry
  HwFindAdapter   ctx=<NT4 HwContext, bus 0 slot 0> cfg.bus=1 cfg.slot=1 ranges=1 range0=FE800000 irq=10
  HwAdapterState  SaveState=255 (TRUE)      <- save real-mode state, before HwInitialize
  HwInitialize    CC=0 CSTS=0 ... returns TRUE, InitComplete=1 (synchronous bring-up)
  startio INQUIRY (op 12, timeout=30)       <- still inside ScsiPortInitialize
DriverEntry exiting
startio TEST UNIT READY, READ CAPACITY, READ LBA 0 / 3F / 40 ...   (volume mount)
```

- `HwFindAdapter` is called from inside `DriverEntry`, through `ScsiPortInitialize`.
  `ConfigInfo` carries the PnP bus and slot and the BAR. The `HwContext` is NT4 style and
  starts at bus 0 slot 0. The inherited scan reads other slots; `ScsiPortGetBusData` gave
  nothing for bus 0 and a garbage vendor ID (`003E`) for 01:00.0, which does not exist.
  Discovery must use only `ConfigInfo->SystemIoBusNumber/SlotNumber` (PLAN 3.1).
- One arrival sends INQUIRY once, then TEST UNIT READY and READ CAPACITY. No other target
  or LUN is probed.
- Re-arrival through the reinstall path also works. After a Device Manager Remove, Refresh
  started the Add New Hardware wizard for "NVM Express Controller (nvme98)" from
  `inf/nvme98-9x.inf` (`a7-wizard-nvme98.png`), installed it and mounted F:
  (`a8-reinstalled-dir.png`).

### Orderly removal: CONFIGMG Query_Remove/Remove_SubTree and Device Manager Remove (run a)

- **Callbacks:** exactly one, `HwAdapterState(SaveState=FALSE)`. The base code shuts the
  controller down there: it deletes the queues, sets CC.SHN, and reads CSTS=0 and CC=0.
  The port sends no `SRB_FUNCTION_SHUTDOWN`, no `SRB_FUNCTION_FLUSH`, no
  SYNCHRONIZE CACHE, no `HwResetBus` and no abort. Device Manager Remove gives the same
  single callback (`debugcon-a.log` seq 85-104 of the third load).
- **Data:** before the callback, IOS and the file system write the pending FAT and FSInfo
  sectors (LBA 0x40, 0x5F, 0x85B; `trace-excerpts.txt`), and nothing is written after it.
  After re-arrival, `fc /b` of a file copied just before the removal shows no differences
  (`a3-rearrival-fc.png`).
- **Volume dismount:** the drive letter goes away ("Invalid drive specification", run b,
  `b4-rearrival.png`).
- **Open files:** with a file open on F: (`type con > F:\HOLD.TXT`),
  `CM_Query_Remove_SubTree` returns 23 (`CR_REMOVE_VETOED`, `a5-query-remove-vetoed.png`).
  The veto works. `cmreenum` then calls `CM_Remove_SubTree` anyway, which forces the
  removal. Windows shows "The volume that was removed had open files on it" and continues
  (`a4-open-files-removed.png`), and the open file's data is lost (`HOLD.TXT` 0 bytes).
  xhci98's CM must honour the veto and not force the removal.
- **Unload:** after the callback returns, the image is unloaded. The next arrival runs
  `DriverEntry` again, the static sequence counter restarts at 0, the device extension
  moves (E45D608C, then E437E08C), and the uncached extension is allocated afresh
  (physical 00FCB000 in the first three loads, 00FAF000 after the Device Manager remove).
- **Re-arrival** after a CONFIGMG remove with the tunnel still up (`cmreenum remove`
  re-enumerates): the device comes back on the same enum key with no reinstall, a fresh
  load, a controller showing CC=0 and CSTS=0, and a working volume.

### Surprise removal (runs a and b)

**Base request path (run a, level 1).** After `tunnel surprise` with the volume idle, a
read is issued and never completes. About 13.2 s later (742.63 s to 755.80 s vm time) the
port calls `HwResetBus`. The base completes everything with `SRB_STATUS_BUS_RESET` but
leaves `NonTaggedInFlight` set, so IOS's retries are answered with BUSY. IOS retries each
request 6 times, splits it into single sectors and retries those 6 times each. Then it
stops sending, but the application stays blocked (`a10-dosbox-hung.png`). A later
CONFIGMG remove still works: the query is vetoed because of that open file, the forced
remove dismounts, and `HwAdapterState(FALSE)` arrives with depth=1 and CSTS all-ones
(`a9-surprise-remove-openfiles.png`). The base shutdown sequence then spends 12.7 s
polling absent hardware inside the callback, and CONFIGMG waits for it. Windows shutdown
then blocks on the hung DOS box (`a11-shutdown-blocked.png`), as in the NVMe evaluation
(W7, W8).

**Gone-state prototype (run b, level 2).**

- *Between requests* (surprise during `copy /b F:\BIG.BIN NUL`): the next `HwStartIo`
  reads CSTS as all-ones, 0.54 s after the gate closed. The driver enters `gone` and
  completes the SRB with `SRB_STATUS_NO_DEVICE`. IOS retries 6 times, splits into sectors
  with 6 tries each, and also tries its FAT and FSInfo writes (0x5F, 0x85B) 6 times each.
  It then returns the error to the application: "General failure reading drive F —
  Abort, Retry, Fail?" (`b1-general-failure.png`). Nothing hangs.
- *With the command outstanding at the fault* (harness `at=fetch op=read nth=50
  act=surprise`, so the read is fetched but never executed): T0 is the gate at
  402.229 s. The timer reads CSTS as all-ones at 402.673 s (`GONE detected in
  FallbackTimer: depth=1`). At the deadline, 418.069 s, the driver calls
  `ScsiPortCompleteRequest(..., SRB_STATUS_NO_DEVICE)`. IOS accepts that completion,
  retries through `HwStartIo` (each retry fast-fails), and reports General failure
  (`b5-deadline-general-failure.png`). The port's own request timeout did not fire in
  those 15.8 s; in run a it fired 13.2 s after the request was issued. That difference was
  not investigated. The prototype completes the held SRBs before any port reset in both
  cases.
- *Afterwards:* IOS keeps the volume, and `dir F:` is served from the cache
  (`b2-dir-cached.png`) until a CONFIGMG remove. `CMR remove` with no open files: the
  query returns 0, then `HwAdapterState(FALSE)` (CSTS all-ones; the base shutdown polls
  for 12.7 s), then "Invalid drive specification" (`b3-remove-after-surprise.png`). After
  `tunnel up` and a re-enumerate, the new endpoint (generation 2 and later) arrives as a
  fresh load and F: works (`b4-rearrival.png`). This was repeated twice in run b.
- `ScsiPortGetBusData` after the removal returns 8 bytes of all-ones (`config probe ...
  id=FFFFFFFF`), so it is a presence signal only, as R4-1 says.

### Shutdown, SYS_CRITICAL_EXIT and RequestTimerCall (runs b, c)

- **System shutdown:** the last I/O is the file system's FAT and FSInfo writes. Then comes
  `HwAdapterState(FALSE)`, the same callback as a CONFIGMG remove, and no I/O follows it
  (`trace-excerpts.txt`, run b). No `SRB_FUNCTION_SHUTDOWN` or FLUSH SRB was seen in any
  run. The only non-media SRBs seen at all were INQUIRY, TEST UNIT READY and
  READ CAPACITY. **The final trigger on 98 SE (G8) is `HwAdapterState(FALSE)`.**
  SYS_CRITICAL_EXIT is not visible to the miniport as a separate event.
- **RequestTimerCall:** it works in normal operation. A 100 ms request fires 100-315 ms
  later in these runs (`trace-excerpts.txt`, ticks `0x40`), so deadlines must be measured
  against a clock, not counted in ticks. Arming it from `HwAdapterState(FALSE)` returns
  normally and does not crash, but the callback never runs: at a CONFIGMG remove it had
  not run 7.7 s later, when the image was reloaded, and at system shutdown it had not run
  before power-off (`debugcon-c.log`, "probe:" lines). Disarming the fallback timer there
  is also harmless (`RequestTimerCall(..., 0)`, "cancelling Fallback Timer"). **After
  `HwAdapterState(FALSE)`, no deferred miniport work runs; that callback must finish
  everything itself, within the stall budget.**

### Tags and mapped buffers (all runs, about 9,400 read/write SRBs)

- **Untagged only.** `SRB_FLAGS_QUEUE_ACTION_ENABLE` was never set and `QueueAction` was
  always 0. `QueueTag` holds a rolling per-request number (01, 04, 05, 06 ...), not a tag.
  At most one SRB is outstanding per LU (`maxdepth=1` in every summary), although the
  miniport advertises `TaggedQueuing` and `MultipleRequestPerLu`. The 9x engine must work
  untagged and must never derive a CID from `QueueTag` (consistent with PLAN 0.2).
  `NonTaggedInFlight` handling decides whether retries succeed: after `HwResetBus` it
  must be cleared.
- **Mapped buffers.** `DataBuffer` was never NULL (`nullbuf=0`) and never below
  0x80000000 (`lowbuf=0`). The addresses are system linear (C0xxxxxx and E4xxxxxx), the
  transfers 512 B to 64 KiB (45,056 B also seen), and `MapBuffers=TRUE` is honoured.
  Retries after errors reuse the same buffer.
- `SrbFlags` are `IS_ACTIVE | ADAPTER_CACHE_ENABLE | DATA_IN` (`0x10240`) for reads.
  Retries add `DISABLE_DISCONNECT | DISABLE_SYNCH_TRANSFER` (`0x1024C`), and `TimeOutValue` is 30 for INQUIRY and 0 for TEST UNIT READY and
  READ CAPACITY.

### PCI config space from runtime callbacks (R4-2, PLAN 3.4)

`ScsiPortGetBusData(PCIConfiguration, own bus, own slot, 8 bytes)` returns 8 with correct
data from `HwStartIo` (during the first INQUIRY) and from the `RequestTimerCall` callback
(`config probe` lines, every run). After a surprise removal it returns all-ones. Results
for other slots are unreliable: 0 for bus 0, and garbage with a non-zero length for a
missing function. The writes were not tested at runtime; the base writes the Command
register only in `HwFindAdapter`/`HwFoundAdapter`. Serialisation: Windows 9x is
uniprocessor, and the port calls the miniport's callbacks one at a time (inferred, not
measured). Which config mechanism SCSIPORT.PDR uses internally was not determined.

**Method named per callback (9x):** `ScsiPortGetBusData` for the miniport's own
function only, from `HwFindAdapter`, `HwInitialize`, `HwStartIo` and the timer callback
(measured for the last two). `ScsiPortSetBusDataByOffset` for the own function in
`HwFindAdapter` (existing use). A runtime write, such as clearing Bus Master Enable for
evidence 4, needs its own test before the contract relies on it. No raw CF8/CFC access.

### G5 on 9x: memory lifetime at stop

The port frees the device extension and the uncached extension after
`HwAdapterState(FALSE)` returns, at both CONFIGMG remove and system exit, whether or not
the controller acknowledged a disable. A remove after a surprise removal reached the
callback with CSTS all-ones and depth=1. The result splits by case:

- **Orderly removal:** passes. The controller is present, and the shutdown inside the
  callback reads RDY=0 within milliseconds, which is evidence 1.
- **Removal after presence loss with G3 evidence already received:** passes, because the
  memory may be released.
- **Removal after presence loss without evidence (MD-1 outcome):** fails for the
  uncached extension, because the port releases it at unload and the miniport cannot
  keep it. The consequence is that on 9x the driver allocates the memory the controller
  can DMA into (queues, PRP pages, bounce buffers) **outside the port**, with VMM
  `_PageAllocate` (fixed, contiguous, physical address known). It frees that memory only
  with evidence, and deliberately leaks it when quarantined. The `.mpd` already calls
  VMM services through `INT 20h` (`utils.c` `_MapPhysToLinear`, `_PageModifyPermissions`),
  so this needs no helper VxD. *Inferred; not yet prototyped.* If the maintainer prefers
  not to leak, a resident VxD owning a quarantine pool across loads would be the
  alternative (see "Helper VxD").

## What IOS and CONFIGMG provide, and what is missing

| Need | Provided by the stock path (98 SE) | Missing, and who covers it |
|---|---|---|
| Enumerate a tunnel brought up after boot | CONFIGMG `Reenumerate_DevNode` on the bridge, then PCI.VXD, then the `*IOS` devloader loads the `.mpd` | The trigger: xhci98's CM (mechanism B), or a user Refresh |
| DCB and volume creation | IOS and SCSIPORT after `HwInitialize` (INQUIRY, READ CAPACITY), then file system mount | Nothing; NVMEVSD.VXD not needed |
| Orderly removal with an in-use check | `Query_Remove_SubTree` vetoes (23) with open files; `Remove_SubTree` dismounts and flushes FS metadata first | The CM must honour the veto (not force) |
| Miniport stop | `HwAdapterState(FALSE)`, once per removal and at system exit | Driver: bounded quiesce, flush and shutdown inside that call (PLAN 0.10, 2.4) |
| Re-arrival | A fresh load per arrival (same enum key, or reinstall from the INF after a Device Manager Remove) | Nothing |
| Surprise-removal notification | None; IOS has no bus-change event (legacy `SRB.H`) | Driver: presence detection (all-ones CSTS); G3 statement from the CM |
| Ending I/O after a surprise removal | IOS retries (6 tries, then per sector), then fails the request to the application; no hang | Driver: complete held SRBs with an error status (`NO_DEVICE` works), never BUSY for removal, clear the untagged slot |
| Dropping the volume after a surprise removal | Only on a CONFIGMG remove or re-enumerate | xhci98's CM (`Query_Remove`/`Remove_SubTree`/`Reenumerate`), or the user |
| Timers | `RequestTimerCall` in normal operation (coarse) | No timer callback after `HwAdapterState(FALSE)` |
| Memory the device may still DMA into after a stop without evidence | None; the port frees its allocations at unload | Driver: VMM `_PageAllocate` outside the port, leaked when quarantined |

## Owners (PLAN 0.12)

| Responsibility | Owner on 9x |
|---|---|
| IOS linkage block (ILB) access | IOS and SCSIPORT.PDR. The miniport never needs the ILB; only a VSD or port driver gets one (NVMEVSD.VXD used it to insert a calldown) |
| DCB identity and lifetime | IOS/SCSIPORT: a new DCB per load, destroyed at CONFIGMG remove. On 9x a returning endpoint always arrives as a new load after a remove: in usb4-emu a re-inserted endpoint has its BAR unassigned until it is re-enumerated (usb4-emu `WIN98-TEST.md`). The in-place reconnect of PLAN 2.6 therefore does not arise on 9x (inferred). Each load re-reads identity from the controller, and the static data does not survive a reload |
| Volume removal and re-arrival | IOS and IFSMgr on CONFIGMG `Remove_SubTree` and `Reenumerate_DevNode`, triggered by xhci98's CM (or the user). The miniport fails I/O quickly while `gone` |
| Callback teardown on unload | SCSIPORT.PDR: no timer callback after `HwAdapterState(FALSE)` (measured), then unload. The miniport finishes its work inside that callback. On Me there is no callback before the unload at all (section "Windows Me"), so the owner there is open: write-through and leaked DMA memory, or a helper VxD |
| Quarantined DMA memory past unload | The miniport, through VMM `_PageAllocate` (not the port's uncached extension) |
| G3 link-down statement on 9x | Open; decided by G3. A VxD service needs a DDB, which an `.mpd` loaded by IOS does not have. If G3 picks a VxD-service interface, that VxD becomes nvme98's helper, and the rows above are unchanged |

## Helper VxD

G9 does not require one. What it would own, if G3 or a maintainer decision brings one in:
the G3 receiving interface (a VxD service, resident across the miniport's unloads), a
quarantine pool of DMA memory that outlives the `.mpd`, and optionally a gone counter or
log that survives reloads. It would not own ILB access, DCB lifetime or volume removal;
IOS and CONFIGMG already do those. NVMEVSD.VXD is not such a helper. From a disassembly
of its LE image (6,544 bytes, from SweetLow's package; his readme says nothing about it),
it is an IOS vendor-supplied driver. It registers with IOS on Sys_Dynamic_Device_Init.
Its AEP handler (functions 0-4) keeps a table of up to 32 DCBs. On config-DCB it accepts a
DCB whose identification at DCB offset 0xA6 matches "nvme2k" (nvme98 no longer reports
that), sets DCB flags and the SG limit, and inserts a calldown. On unconfig-DCB it drops
the DCB. Its request routine splits read, write and verify requests at
scatter/gather fragments that are not page-contiguous into child IOPs. It is a data-path
workaround for the base PRP construction (PLAN 0.4 replaces it) and has no lifecycle
role. Its absence did not affect anything above.

## Consequences for the plan

- **0.12 / G9 on Me: blocked pending a maintainer decision** (section "Windows Me"). Me's
  port has no stop or shutdown callback. The choice is between write-through plus leaked
  DMA memory at every removal, and a helper VxD (IOS VSD) that takes the stop and the
  shutdown. G5 and G8 for Me follow from that choice.
- **0.12 / G9: pass for 98 SE.** No helper VxD, so no VxD build target, INF install or
  load-order work items in phase 0. `inf/nvme98-9x.inf` stays as it is, and NVMEVSD.VXD
  stays out.
- **2.7 (9x lifecycle contract):** inputs from this gate. Final trigger and stop are both
  `HwAdapterState(FALSE)`. `HwAdapterState(TRUE)` comes once per load before
  `HwInitialize`. No SHUTDOWN or FLUSH SRB arrives. Operation is untagged at depth 1.
  Buffers are mapped. There is no deferred work after the stop. Removal, rescan and
  re-arrival are CONFIGMG-driven, with a fresh load each time. The RMW drain (PLAN 2.7)
  must finish inside `HwAdapterState(FALSE)`.
- **2.2 on 9x:** `SRB_STATUS_NO_DEVICE` ends IOS's retries after 6 tries per request
  (plus the per-sector split). That is the 9x answer to "which status stops retries",
  measured with no sense data. Fast-fail must also cover the untagged slot
  (`NonTaggedInFlight`).
- **0.10 gone deadline:** measure it against a clock (TSC or VMM system time), not timer
  ticks. Ticks ran up to 3x slower than requested.
- **0.5 and G5 on 9x:** DMA memory moves out of the port's uncached extension, and is
  freed only with evidence (see G5 above). Prototype this before 0.10 on 9x. If it fails,
  G5's "blocked pending a maintainer decision" applies to 9x for the no-evidence case.
- **3.1 / 3.4 on 9x:** discovery uses `ConfigInfo`'s bus and slot, not the NT4
  `HwContext` scan. Config reads use the own function only, from the callbacks named
  above. A runtime Bus Master Enable write still needs a test.
- **2.4:** the base shutdown path stalls 12.7 s on absent hardware inside
  `HwAdapterState(FALSE)` (5 s polls). It must stop at the first all-ones read.
- **G8 (9x row):** the final trigger is `HwAdapterState(FALSE)`; there is no
  `SRB_FUNCTION_SHUTDOWN`.
- **xhci98 CM (REENUM-EXPERIMENT.md):** on a tunnel-down, call `Query_Remove_SubTree` and
  respect a veto. Forcing `Remove_SubTree` loses open-file data. Note that with the gate
  already closed, the removal is a surprise removal from the driver's point of view.

## Limits

- **Windows Me** was run later on a stock install (section "Windows Me"). Its limits are
  listed there.
- **The IOS stack is QuickInstall's updated set,** not gold 98 SE (Setup table). A gold
  install might differ, notably in IOS 2010 versus 1999 retry behaviour. For the stop, the
  gold 98 SE `SCSIPORT.PDR` (23,650 bytes, 1999) was run on this image and calls

### Verdict (Me)

**Blocked pending a maintainer decision.** No helper VxD is needed for the IOS lifecycle.
Arrival, dismount, re-arrival, the open-file veto and the end of I/O after a surprise
removal all behave as on 98 SE. **The stop is missing, though.** Me's SCSIPORT.PDR never
calls `HwAdapterState(FALSE)`, at removal or at shutdown, and sends no SHUTDOWN or FLUSH
SRB. The miniport therefore gets no chance to quiesce, flush, disable or shut down the
controller:

- **G5 fails on Me, even for an orderly removal.** The port unloads the image and frees
  the device extension and the uncached extension while the controller is still enabled,
  with its queues pointing into that memory.
- **G8 has no final trigger on Me.** Me powers off a few seconds after the last file
  system write, and the controller never sees CC.SHN.

### Results by scenario (Me)

**Arrival (runs a, b, c).** It is the same as on 98 SE. `C:\CMR scan` re-enumerates the
bridge, and PCI.VXD and the `*IOS` devloader load the `.mpd`. The call order is
`DriverEntry`, `HwFindAdapter` (ConfigInfo bus 1 slot 1, BAR FE800000, IRQ 10),

mounts (`a1-arrival-dir.png`). The NT4-style scan of bus 1 slot 0 again reads garbage
(VID D7C0, A818, 0818, 07C0 on different loads).

**Orderly removal: no stop callback (runs a, c).**

- `C:\CMR remove` right after `COPY D:\CMREENUM.EXE F:\T1.BIN`: the query returns 0 and
  the remove returns 0 (`a2-cmr-remove.png`). The file system first writes FAT, FSInfo
  and the data (`trace-excerpts.txt`, run a). Then the image is unloaded: the next load

  the callback it hangs on never came.

**Open-file veto.** It is the same as on 98 SE. With `TYPE CON > F:\HOLD.TXT` open,
`CM_Query_Remove_SubTree` returns 23 (`a5-query-remove-vetoed.png`). The forced

**Surprise removal, base request path (run a, level 1).** It is the same as on 98 SE.
`HwResetBus` came **22.7 s** after the outstanding request was issued (98 SE: 13.2 s,
TCG time). It found CSTS all-ones. `NonTaggedInFlight` stayed set, so IOS's retries got
BUSY, IOS stopped sending, and the DOS box hung (`a9-dosbox-hung.png`). A CONFIGMG remove
was vetoed (23) and then forced through (`a10-surprise-remove-openfiles.png`,
`a11-surprise-remove-vetoed.png`). **Without a stop callback there was also no 12.7 s
stall** in the base shutdown code. Shutdown was blocked by the hung DOS box ("You must
quit this program", `a12-shutdown-blocked.png`). After End Task twice, Me powered off.

**Surprise removal, gone prototype (run b, level 2).**

- *Between requests:* GONE was detected in `HwStartIo` and requests fast-failed with
  `SRB_STATUS_NO_DEVICE`. The retry pattern is the same as on 98 SE: 1 + 5 tries with
  `DISABLE_DISCONNECT | DISABLE_SYNCH_TRANSFER`, then a split into sectors with 6 tries
  each, and the same for the FAT reads. Then "General failure reading drive F"
  (`b1-general-failure.png`). Nothing hangs.
- **Difference from 98 SE:** after Fail, `dir F:` was not served from the cache. It went
  to the device and also failed with General failure (`b2-dir-general-failure.png`).
- *Afterwards:* `CMR remove` returned 0 for the query, with no callback, and then gave
  "Invalid drive specification" (`b3-remove-after-surprise.png`). After `tunnel up` and a
  scan, the new endpoint (generation 2) arrives as a fresh load with `CC=0`, and F: works
  (`b4-rearrival.png`).
- *With the command outstanding at the fault* (`at=fetch op=read nth=50 act=surprise`):
  the gate closed at 448.025 s. The timer saw CSTS all-ones at 448.586 s (0.56 s later).
  At the deadline, 463.985 s (15.96 s after the gate), the driver called
  `ScsiPortCompleteRequest(NO_DEVICE)`, and IOS reported General failure
  (`b5-deadline-general-failure.png`). The port's own timeout did not fire before the
  deadline. This is the same as on 98 SE.

**Shutdown (runs a, b, c, prep).** The last I/O is the file system's FAT and FSInfo
writes (LBA 0x40, 0x5F, 0x85B). About 6 s after the Shut Down dialog's OK, the guest
powers off through ACPI. No `HwAdapterState(FALSE)` was seen with the volume mounted, in
any of the four runs. There was no SHUTDOWN or FLUSH SRB, and no CC write
(`trace-excerpts.txt`). **Me has no miniport-visible final trigger.**

**RequestTimerCall.** It works in normal operation. Back-to-back 100 ms requests fired
100 ms to 1.5 s apart (`trace-excerpts.txt`), so deadlines must again be measured against
a clock. Behaviour after a stop could not be measured, because no stop callback arrives.

**Tags, buffers, SRBs.** These are the same as on 98 SE. All I/O is untagged with
`QueueAction` 0, `maxdepth=1`, `nullbuf=0` and `lowbuf=0`. Buffers are system linear
(C1xxxxxx-C7xxxxxx, E4xxxxxx). The flags are `0x10240` for reads, `0x10280` for writes,
and `0x1024C`/`0x1028C` on retries. Transfers are at most 61,440 bytes (98 SE: up to
64 KiB). **One difference:** `TimeOutValue` is 30 for INQUIRY, but for TEST UNIT READY
and READ CAPACITY it is often garbage (C3xxxxxx and E4xxxxxx values, which look like
pointers) instead of 0. The driver must not derive a timeout from `TimeOutValue` on 9x.

**Config space.** `ScsiPortGetBusData(own bus/slot, 8)` returns 8 with correct data from
`HwStartIo` and from the timer callback. After a surprise removal it returns 8 bytes of
all-ones, as on 98 SE.

**Me specifics.**

- *System Restore* is on by default. During prep it created `_RESTORE` on the transfer
  disk, which was then a writable vvfat fixed disk. It wrote nothing to the hot-added
  NVMe volume during the runs (`7z l` of run a's NVMe overlay: only `BIG.BIN`,
  `README.TXT`, `T1.BIN` and `HOLD.TXT`).
- *No real-mode DOS boot*, but `HwAdapterState(255)` still arrives once per load, before

- *PCI.VXD* (inside VMM32.VXD): no difference was seen. BAR assignment, IRQ 10 routing,
  re-enumeration and generation-2 re-insertion behave as on 98 SE.

### What the Me result means

| Missing on Me | Options (maintainer decision, none chosen) |
|---|---|
| Stop at removal: nothing disables the controller before the port frees its memory | (a) DMA memory outside the port (VMM `_PageAllocate`, as already proposed for 98 SE). It is leaked at **every** Me removal, because no removal there ever has evidence; the next load resets the controller before reuse. (b) A helper VxD. A resident IOS VSD sees `AEP_UNCONFIG_DCB` (NVMEVSD.VXD's AEP handler shows the hook) and can quiesce and disable the controller and own a quarantine pool across loads. *Inferred, not prototyped* |
| Final trigger at shutdown: the controller never sees CC.SHN, so every Me power-off is an unsafe shutdown with the volatile write cache unflushed | (a) Write-through on Me: turn off the volatile write cache (Set Features VWC) or write with FUA, at a performance cost, so that no shutdown flush is needed. (b) A helper VxD that receives `AEP_SYSTEM_SHUTDOWN`/`System_Exit` and runs the shutdown sequence. *Inferred, not prototyped.* Whether an `.mpd` can register a system-exit callback without a DDB was not tested |
| Stall budget | Nothing to do: with no stop callback, Me never runs the base's 12.7 s poll |

`HwAdapterState(FALSE)` remains the 9x stop and final trigger, but only where the port
calls it (QuickInstall's 98 SE port, measured). The driver must not depend on it for
correctness. The follow-up evidence, including `CachesData = TRUE` for the shutdown row,
is in "Windows Me stop investigation" below.

### Windows Me stop investigation

Run 2026-10-15, after the Me result above, to gather evidence for the pending decision. The
evidence is in [G9/me-stop/](G9/me-stop/): `debugcon-m4.log`, `debugcon-m5.log` (Me),
`debugcon-s2.log` (98 SE), [trace-excerpts.txt](G9/me-stop/trace-excerpts.txt) and the PNG
files. Static analysis was done on the three `SCSIPORT.PDR` builds and the 98 SE and Me
`IOS.VXD` (LE images loaded with their fixups and disassembled with binutils `objdump`; VxD
service numbers named from the Windows 98 DDK `*.INC` files). Nothing was patched and no
disassembly is committed; addresses below are offsets in the loaded objects.

**Root cause: Windows Me's IOS, not its SCSIPORT.PDR.**

| Binary | Source | Size, date |
|---|---|---|
| `SCSIPORT.PDR`, gold 98 SE | 98 SE CD (`D:\isos\Win98SE.iso`), `WIN98\BASE4.CAB` | 23,650, 1999-04-23 |
| `SCSIPORT.PDR`, QuickInstall | `vms/win98/win98.qcow2` | 23,674, 2001-01-09 |
| `SCSIPORT.PDR`, Me | Me CD (`D:\isos\Windows Me OEM Full.iso`), `WIN9X\BASE2.CAB` | 26,957, 2000-06-08 |
| `IOS.VXD`, gold 98 SE / QuickInstall / Me | same CABs; QuickInstall's from `SYSTEM\VMM32\`; Me's is linked into `VMM32.VXD` on an installed system | 69,570 / 69,594 / 80,147 |

1. **The three port builds handle the same events in the same way.** Each registers one
   asynchronous event routine (AER) per miniport (through `IOS_Register`). Its dispatch table
   has handlers only for `AEP_INITIALIZE`, `AEP_SYSTEM_CRIT_SHUTDOWN`, `AEP_BOOT_COMPLETE`,
   `AEP_CONFIG_DCB`, `AEP_IOP_TIMEOUT`, `AEP_DEVICE_INQUIRY`, `AEP_SYSTEM_SHUTDOWN`,
   `AEP_UNINITIALIZE` and `AEP_SYSTEM_REBOOT`. Every other code, including `AEP_UNCONFIG_DCB`,
   `AEP_PEND_UNCONFIG_DCB` and the power message, goes to a no-op. The handlers are
   instruction-for-instruction the same in all three (gold 98 SE `0x21B74`-`0x21C79`, Me
   `0x31B0C`-`0x31C11`), and all three make the same 84 VxD service calls. Me's extra 3 KB
   are a table of symbol names at the end of the file; its code objects are slightly
   smaller.
2. **Where the port calls the miniport's stop.** `HwAdapterState(DeviceExtension, Context,
   FALSE)` is called from two places:
   - `AEP_SYSTEM_CRIT_SHUTDOWN`, unconditionally (if the miniport set `HwAdapterState`);
   - `AEP_UNINITIALIZE` (sent when IOS destroys the adapter's DDB), **only if bit `0x04` of
     `DDB_ios_flags` is set** (byte `0x11` of the IOS DDB; the Windows 98 DDK `DDB.H` names
     `0x04` `DDB_IOS_FL_PLEASE_DESTROY`). After that call the handler releases the port's DMA,
     IRQ and timer resources.

   `SRB_FUNCTION_SHUTDOWN` is sent from `AEP_SYSTEM_SHUTDOWN` and `AEP_SYSTEM_REBOOT`, one SRB
   per DCB of the adapter, **only if the miniport set `CachesData`** in
   `PORT_CONFIGURATION_INFORMATION`. The port copies `CachesData` into adapter flag `0x04`
   after `HwFindAdapter`, and only this handler tests it. The port builds only two
   kinds of SRB itself, `EXECUTE_SCSI` and this `SHUTDOWN`; it never builds
   `SRB_FUNCTION_FLUSH`.
3. **What IOS sends.** The 98 SE IOS's control procedure maps `System_Exit` to
   `AEP_SYSTEM_SHUTDOWN`, `Sys_Critical_Exit` to `AEP_SYSTEM_CRIT_SHUTDOWN`, and
   `Device_Reboot_Notify` to `AEP_SYSTEM_REBOOT`. Gold and QuickInstall builds are alike
   here. **Me's IOS has no `Sys_Critical_Exit` case and broadcasts `AEP_SYSTEM_CRIT_SHUTDOWN`
   nowhere.** It keeps `System_Exit` and `Device_Reboot_Notify`.
4. **Why the 98 SE removal stop exists at all.** On `CONFIG_ENUMERATE`, the 98 SE IOS marks
   the adapter's DDB as enumerated with `bts word [ddb+0x11], 2`, which sets value `0x04`.
   The DDK defines that "first enumeration done" flag as bit number 2, so it collides with
   `DDB_IOS_FL_PLEASE_DESTROY` (value 4). The port's `AEP_UNINITIALIZE` test therefore
   passes for every adapter that has been enumerated. Me's IOS uses bit 3 (`0x08`) for that
   flag, and nothing in Me's IOS sets `0x04`. Measured: `DDB_ios_flags` at the stop is
   `07` at a 98 SE remove and `06` at a 98 SE shutdown (`debugcon-s2.log` lines 91 and 268),
   and `0A` on Me at shutdown (`debugcon-m4.log` line 187). **The 98 SE stop at removal
   depends on this flag collision.** Me removed the collision and, with it, the only
   removal stop the port has.

**Gold 98 SE (question 1).**

- *Gold `SCSIPORT.PDR` on the 98 SE image* (run s2, QuickInstall's IOS): the stop arrives at
  a CONFIGMG remove (`debugcon-s2.log` line 88: CC.SHN, then CC=0) and at shutdown (line 265).
  This is the same as QuickInstall's port.
- *Gold `IOS.VXD` as well* (run s1): with the gold IOS copied into `SYSTEM\VMM32\` of the
  QuickInstall image, 98 SE hung at the desktop after the restart (`s1-gold-ios-hang.png`).
  It does not mix with QuickInstall's newer `DISKTSD`/`ESDI_506` set. No fully gold
  install exists locally (xhci98 `tools\w98se.img` is a boot floppy, and
  `tools\win98se-extracted` holds only USB/WDM files). From the static analysis, the gold
  IOS has the same control procedure and the same `bts ..., 2`, so **gold 98 SE behaves
  like the measured 98 SE runs** (*inferred*).
- *Me's `SCSIPORT.PDR` on 98 SE* (run s3): the guest hung after the CONFIGMG scan, before
  `DriverEntry` (`s3-me-port-on-98se-hang.png`, `trace-excerpts.txt`). *QuickInstall's port
  on Me* (run d above) stopped in `HwFoundAdapter` after the line "Controller Registers
  PTE", in the next call, `ScsiPortGetUncachedExtension`. Why each hang happens was not
  determined. Neither swap is needed, because the event handling in the three builds is
  identical (point 1).

**Workarounds without a VxD (question 3).**

- **`CachesData = TRUE` gives Me a final shutdown trigger** (runs m4 and m5, levels 4 and
  5). At system shutdown Me sends `SRB_FUNCTION_SHUTDOWN` after the last file system write
  (`startio func=07`, `debugcon-m4.log` line 183; `debugcon-m5.log` line 406). The base
  driver's flush completes, and a `RequestTimerCall` armed in that SRB still runs 71 and 35
  ticks later. Then the guest powers off (`trace-excerpts.txt`, m4 and m5). **On 98 SE the
  same build received no SHUTDOWN SRB at shutdown** (run s2), only `HwAdapterState(FALSE)`.
  `CachesData` changes nothing else in the port. Restart on Me should send the same SRB
  through `AEP_SYSTEM_REBOOT` (*inferred*, not run).
- **No registry switch or other callback.** The port reads only `AdapterSettings`,
  `ForceReboot` and `PollingSupportNeeded` from the registry. The 9x
  `HW_INITIALIZATION_DATA` has no `HwAdapterControl`. Nothing else reaches the miniport at
  a Me removal: `AEP_UNCONFIG_DCB` and `AEP_PEND_UNCONFIG_DCB` go to the no-op.
- **Experiment: set `DDB_ios_flags` bit `0x04` from the miniport** (level 5, run m5). The
  device extension is at `DDB+0x8C` in all three port builds (the `HwAdapterState` call site
  passes `DDB+0x8C`). Measured: `DeviceExtension - 0x8C` holds a DDB with signature
  `0x4442` and plausible DCB, DVT and devnode pointers. At the first read the test build
  sets the bit (`iosflags` `02` to `06`, `debugcon-m5.log` lines 68-69). Result on Me:
  - **The stop arrives at a CONFIGMG remove**, twice. It comes after the file system's
    writes (FAT, data, FSInfo), then CC.SHN, RDY=0 and CC=0 (`debugcon-m5.log` lines
    92-113, 271; `trace-excerpts.txt`).
  - The next load finds `CC=0 CSTS=0`, F: works, and a file copied just before the second
    remove compares equal (`m5-rearrival-fc.png`).
  - Shutdown is unchanged: `SRB_FUNCTION_SHUTDOWN` only. Me has no `AEP_SYSTEM_CRIT_SHUTDOWN`,
    and IOS does not destroy DDBs at shutdown.

  The flag is IOS-private ("read only for non-IOS" in `DDB.H`). The `DDB+0x8C` offset is
  internal to SCSIPORT. Me's IOS also tests `0x04` in one place: its port-driver
  inquiry loop sends a DDB that has the bit set down a destroy path that calls
  `CONFIGMG_Remove_SubTree` (static analysis, not traced further). That code
  is identical in the 98 SE IOS, where every enumerated DDB has the bit set, so the
  experiment puts Me in the state 98 SE always runs in. That makes it plausible, not
  proven. A removal before the first read gets no stop. Not tested: Device Manager Remove
  and Disable, removal after a surprise removal, more than one adapter, standby and
  hibernate.

**A helper IOS VSD (question 4), design only.** It was not built.

- *Load and registration:* a static `.VXD` in `SYSTEM\IOSUBSYS` (as NVMEVSD.VXD was),
  copied by `inf/nvme98-9x.inf`. On `Sys_Dynamic_Device_Init` it calls `IOS_Register` with a
  DRP in a vendor layer (`DRP_VSD_1`..`9`), an AER and an ILB.
- *Finding nvme98's DCB:* at `AEP_CONFIG_DCB`, match the physical DCB by bus type SCSI and
  the INQUIRY vendor/product nvme98 reports, or by its DDB's DVT. Keep a small table, as
  NVMEVSD.VXD did.
- *Stop at removal:* Me's IOS sends `AEP_PEND_UNCONFIG_DCB` and then `AEP_UNCONFIG_DCB` for
  each DCB of the DDB, before it sends `AEP_UNINITIALIZE` to the port (Me IOS DDB-destroy
  routine at `0x50DA1`-`0x50DE5`, static analysis). On either one, the VSD sends an `SRB_FUNCTION_SHUTDOWN`
  request down to the DCB, the same request SCSIPORT builds at `AEP_SYSTEM_SHUTDOWN`. The
  port then serialises it with other I/O, and the miniport already handles it. The
  alternative is setting `0x04` in the DDB's `DDB_ios_flags` from the VSD. That is the
  documented field name, but the semantics are still IOS-private.
- *Shutdown:* not needed with `CachesData = TRUE`. Otherwise the VSD handles
  `AEP_SYSTEM_SHUTDOWN` the same way.
- *What else it could own:* the G3 link-down interface (a VxD service) and a quarantine
  pool for DMA memory that outlives the `.mpd`.
- *Toolchain:* everything needed is local. The Windows 98 DDK is in xhci98
  `tools\win98ddk\win98se_ddk.exe`, extracted in `tools\win98ddk-extracted`. It has
  `ML.EXE` 6.11d and `LINK.EXE` 5.12 (`/VXD`) in `all\BINS_DDK`, `VMM.INC`, `IOS.INC`,
  `AEP.INC`, `DRP.INC`, `ILB.INC` and `ISP.INC` in `incs`, and `DCB.INC`, `IOP.INC`,
  `SRB.INC` and the `HELPVSD` sample VSD in `all\BLCK_DDK`. MSVC 6.0 in `tools\MSVC600`
  could build a C VSD with VXDWRAPS. Nothing is missing. The files would be copied into
  nvme98's git-ignored `tools\` (never committed, AGENTS.md).
- *Effort (estimate):* about 300-500 lines of MASM written from scratch against the DDK
  headers. Then a build step, the INF change, and test runs on 98 SE and Me for arrival,
  remove, Device Manager Remove, surprise removal and shutdown. Roughly 1-2 days. The
  ongoing cost is a second binary to ship, install and keep loaded on both 98 SE and Me.

**What the evidence means for the pending decision** (no option chosen here):

| Need on Me | Without a VxD | With a VSD |
|---|---|---|
| Final trigger at shutdown (G8) | `CachesData = TRUE`: `SRB_FUNCTION_SHUTDOWN` arrives after the last write; flush, then CC.SHN there (measured). Write-through is not needed for shutdown | Same, or `AEP_SYSTEM_SHUTDOWN` in the VSD |
| Stop at removal (G5) | (a) none: leak DMA memory at every Me removal, and write-through (VWC off or FUA) because the volatile cache is never flushed before the CM drops the tunnel; or (c) the `DDB_ios_flags` experiment: stop measured, undocumented | SHUTDOWN SRB at `AEP_PEND_UNCONFIG_DCB`, in documented AEP terms (*inferred*, not prototyped) |
| 98 SE | Unchanged: `HwAdapterState(FALSE)` at removal and shutdown. With `CachesData = TRUE` still no SHUTDOWN SRB at 98 SE shutdown (measured), so the driver must accept either trigger | Unchanged |

The driver must treat **whichever comes first** of `SRB_FUNCTION_SHUTDOWN` and
`HwAdapterState(FALSE)` as the final trigger, and must handle any later I/O by re-enabling
the controller first (G8's rule).
