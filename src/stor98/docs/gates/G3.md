# Gate G3: CM link-down notification

> Prototype source is not on `main`; it stays on the gate branch `phase0-g3g6`: the G1/G8
> deferred bring-up (759d860) with the G2/G4 gone state cherry-picked (3dd4431, 3807e3a), plus
> 4e1e55d (receiving side, interface proposal, CM stand-in) and the G6 commits. Shared with
> [G6.md](G6.md).

PLAN 0.0, G3: can xhci98's CM tell nvme98 that it has torn down the tunnel carrying the
controller, sent only after completed quiescence (0.10, evidence 2, boundary M1) and before the
OS removal path starts? The CM owns the sending side; nvme98 owns the receiving interface.

**Pass condition (two stages, R4-7).** Interface prototype: delivered on 98 SE and on one NT
port, interface named. Per-port qualification on every OS that relies on G3: (1) delivery at
every injection point; (2) ordering: after completed quiescence (host trace: the statement's
marker is later than `usb4_tp_cutoff`) and before that OS's first removal callback; (3)
delivered within the gone deadline with the port's queues full of held SRBs (on NT the
IOCTL must not queue behind them).

Date: 2026-10-15. usb4-emu `src/qemu/build` binary of 2026-10-15 01:42, copied to
`vms/nvme98-g36/bin`. TCG, i440FX, `usb4-tunnel-bridge` (SHPC), `shpc-autoenable=on`.

**Selected design: interface 2** (a CM-owned link-state block that nvme98 polls from its own
timer and `HwStartIo`), on NT; the same block, found another way, on 9x (below). Interface 1
stays useful as a diagnostic query (`NVME98CM_CODE_QUERY`) only.

Consequence for PLAN: qualification (3) rules out any port-routed request (IOCTL, pass-through,
IOS request) as the evidence-2 carrier on NT, because the port admits it only into a free
slot of the LU it addresses. The gone deadline (MD-1) then wins the race. Interface 2 is
outside the miniport contract (direct `ntoskrnl` imports, like MD-3 (b)); that is a decision
for the maintainer (below, "Decision needed").

## Interface proposal (for xhci98's CM)

Header: `src/nvme98cm.h` on `phase0-g3g6` (4e1e55d). On `main` the interface definition is
[`include/nvme98cm.h`](../../include/nvme98cm.h): the same definitions, its comments updated
for the maintainer's decision MD-6 (interface 2 adopted, interface 1 diagnostic only), and
licensed separately as a BSD-3-Clause interface so that xhci98 (GPL-2.0) can include it
unchanged. Two interfaces share the
statement's meaning: **"the PCIe link to function (bus, slot) went down, the tunnel's PCIe
path is closed and the endpoint reset (A1) has completed"** (0.10 evidence 2, MD-2).

### Interface 2 (selected): link-state block

- **Owner and lifetime.** The CM allocates one `NVME98LS_TABLE` in non-paged memory and never
  frees it, not even at its own unload (a few hundred bytes). nvme98 may keep a pointer to it
  for as long as an adapter instance lives, and on NT the miniport gets no callback before its
  image is unloaded after a surprise removal (G2, G5), so nvme98 must not register anything
  with the CM either.
- **Rendezvous (NT).** The CM creates the callback object `\Callback\Nvme98LinkState`
  (`ExCreateCallback`, `OBJ_PERMANENT`) and registers one callback. For
  `Argument1 == NVME98LS_QUERY` ('N98L') it stores the table address in
  `*(PNVME98LS_TABLE *)Argument2`. nvme98's `HwFindAdapter` (PASSIVE_LEVEL) opens the object
  without creating it and calls `ExNotifyCallback` once; a missing object (no CM) means no
  evidence 2 on that system (MD-1 applies). The CM must be started before the endpoint can be
  enumerated (it is: it establishes the tunnel).
- **Entry.** One per tunnelled function: `BusNumber`, `SlotNumber` (`PCI_SLOT_NUMBER`),
  `LinkGeneration`, `Flags` (`IN_USE`, `UP`, `DOWN_QUIESCED`), `AckGeneration` (written only
  by nvme98) and `Sequence` (odd while the CM updates the entry; a seqlock).
- **CM obligations.**
  1. Tunnel established: `LinkGeneration++`, `Flags = IN_USE | UP`, **before** the OS can
     enumerate the endpoint (before `IoInvalidateDeviceRelations` / `Reenumerate_DevNode`).
  2. Tunnel down: only after the PCIe path is closed and the endpoint reset has completed
     (MD-2 obligation 2), `Flags = IN_USE | DOWN_QUIESCED`.
  3. Then wait for `AckGeneration == LinkGeneration`, at most the gone deadline (5 s in the
     test build), **and only then** start the OS removal path (bridge `BusRelations`
     invalidation on NT, `Query_Remove_SubTree`/`Remove_SubTree` on 9x).
  4. Never re-establish a tunnel to an endpoint that was not reset (MD-2 obligation 1).
- **nvme98.** Records `LinkGeneration` at `HwFindAdapter`. Polls the entry from the watchdog
  tick, the bring-up timer and `HwStartIo` (port-synchronised contexts). `DOWN_QUIESCED` with
  a generation equal to or newer than the recorded one is evidence 2: held SRBs complete with
  `SRB_STATUS_NO_DEVICE` (2.2), the held commands' DMA memory is released, the gone deadline
  is cancelled, `BusChangeDetected` is notified, then `AckGeneration` is written. `DOWN`
  without `QUIESCED`, or for an older generation, is ignored.
- **Latency.** One watchdog tick (100 ms nominal, 15.6 ms timer granularity on 2000 and XP
  x64) while SRBs are held or `gone`; at the next `HwStartIo` when idle (nothing is held then,
  so nothing waits for it; the CM's acknowledgement wait times out). A product build can keep
  a slow (1 s) tick while running to acknowledge idle adapters too.

### Interface 1 (diagnostic only): `IOCTL_SCSI_MINIPORT`

`SRB_IO_CONTROL.Signature = "NVME98CM"`, `ControlCode` `NVME98CM_CODE_QUERY` or
`NVME98CM_CODE_LINK_DOWN`, payload `NVME98CM_MSG`, sent to `\Device\ScsiPortN`. nvme98 takes
the SRB in `HwStartIo` before its target check. Return codes: `ACCEPTED`, `BAD_REQUEST`,
`NOT_THIS_FUNC`, `CONTRADICTED` (the function still answers with CC.EN or RDY set),
`NOT_QUIESCED`, `ALREADY`. Measured limits, any one of which disqualifies it as the evidence
carrier:

- The port routes it to LU 0 (`PathId 0, TargetId 0, Lun 0` in every run) and starts it only
  when that LU has a free slot. With 10 SRBs held at the miniport and 22 more queued in the
  port (gio QD 32), it was started only after the MD-1 deadline freed the slots (2000:
  7 968 ms after T0; XP x64: 5 739 ms). It was not FIFO-queued behind the 22: it was started
  first once a slot freed.
- After `BusChangeDetected` removed the disk (LU gone), it fails with `0xC00000C0`
  (`STATUS_DEVICE_DOES_NOT_EXIST`), so it cannot reach an adapter with no disk (identify
  failed, bring-up failed, or after an earlier statement or deadline).
- While the G1 bring-up holds an SRB (no `NextRequest`), the port sends nothing else to the
  miniport (G1), so it cannot be delivered during bring-up either (inferred from G1's design;
  not run with interface 1 alone).

## Prototype and stand-in

- nvme98 (`src/g36.c`, `src/g36ls.c`, hooks in `nvme2k.c` and `g24.c`): G24 gone state plus a
  `LINKDOWN` state (path-down row of 0.10). Stage codes 0x90-0x96 (`src/dbgport.h`).
- `tests/cmstub/cmstub.sys`: NT legacy driver standing in for xhci98's CM. A system thread
  polls the tunnel bridge's SHPC slot status (config capability 0x0C, DWORD select 9, presence
  bits 11:10) every 10 ms. usb4-emu marks the slot empty in stage 3 of a tunnel down, after
  stage 2 (endpoint reset and drain; `docs/ARCHITECTURE.md` 4.4), so "slot empty" is a stand-in
  for "the CM has completed the teardown". It then writes the block (and/or sends the IOCTL),
  waits for the acknowledgement and logs every step to the usb4-emu debug port (codes
  0xC0-0xC6, with TSC markers). Registry parameters: `Mode` (0 after the slot goes empty; 1
  early, as soon as the endpoint's config reads all-ones, i.e. at stage 1), `Interface` (1
  IOCTL, 2 block, 3 both), `NoFlag`, `DelayMs`.
- Workload `tests/gio` (unbuffered overlapped reads, QD 8 or 32, 64 KiB). Stimulus: harness
  `x-faults` holds every read from the 150th at fetch; the tunnel is taken down by `act=surprise`
  on the 157th fetch (exactly 8 held) or by QMP `tunnel surprise` a few seconds later
  (saturation: 10 held at the miniport, 22 queued in the port).
- Ordering is read from the host trace by `vms/nvme98-g36/g3log.py`: `usb4_tp_cutoff` <
  CM "slot empty" marker < CM send marker < nvme98 receipt marker (all `host_ns`).

Ordering against the OS removal path: in every run the OS removed the **controller** only at
the stand-in's (or the harness's) later rescan, after the acknowledgement. 2000 and XP x64 on
i440FX have no SHPC driver, so nothing removes the controller before the CM asks. The only
removal that came earlier was the **disk** PDO, and nvme98 caused it itself with
`BusChangeDetected` after applying the statement (the "Unsafe Removal" dialog names only the
disk). On q35 with native PCIe hot-plug (Windows 7) the OS reacts to the stage-3 presence change
on its own, in parallel with the CM; that race is not measured (7 x64 not run).

### Observations

- `ScsiPortGetSrb`-based tracking (G24) and the block are independent: held SRBs were always
  still port-owned when completed (port-retired 0).
- The harness's `act=surprise` closes the gate synchronously; stage 2 completes 0.3-0.8 ms
  later in every run, and stage 3 (slot empty) is what the stand-in polls, so in the emulator
  the statement can never precede the cutoff unless the CM bypasses stage 3 (run E).
- Memory: the PRP-page bitmap of the held commands (0xff, 0x3ff, 0x9e) was released on
  evidence 2; with the MD-1 outcome it stays quarantined (G2).
- On 2000 the port started at most 10 tagged SRBs on the LU in these runs (QD 32 workload);
  the IOCTL needs one of those slots.

## Windows 9x receiving interface (design; not prototyped)

There is no `IOCTL_SCSI_MINIPORT` on 9x, and an IOS request (an IOP through the DCB) would
queue behind the held request exactly like the NT IOCTL. The 9x receiver should therefore be
the **same link-state block, polled from the miniport's `RequestTimerCall` callback and
`HwStartIo`**, with a 9x rendezvous. The `.mpd` already calls VMM services through `INT 20h`
(G9), and xhci98's CM on 98 is a WDM driver that already calls CONFIGMG through the `INT 20h`
dynalink from a system thread (usb4-emu `docs/REENUM-EXPERIMENT.md`, mechanism B). Options, in
order of preference:

1. **Helper VxD owns the block (if MD-5 option (i) adds the helper VSD).** The VSD allocates
   the block at `Sys_Dynamic_Device_Init`/`Device_Init` (`_HeapAllocate` or `_PageAllocate`,
   fixed, never freed) and publishes it as its `DDB_Reference_Data`. Both the `.mpd` (in
   `HwFindAdapter`) and the CM (from its system thread) find it with VMM `Get_DDB` by the
   VxD's name and read the reference data. No registry, no pointer validation problem, and the
   block lives in a module that is never unloaded. The same VSD would deliver Me's missing stop
   (MD-5 (i)) and could own the 9x quarantine pool (MD-4), so one binary serves three items.
2. **Registry rendezvous, no helper VxD.** The CM allocates the block from NTKERN non-paged
   pool (global system arena, fixed) and writes its linear address with a random cookie to
   `HKLM\System\CurrentControlSet\Services\nvme98\LinkState` (or the controller devnode's
   hardware key through CONFIGMG `Write_Registry_Value`). The `.mpd` reads it once in
   `HwFindAdapter` with VMM `_RegOpenKey`/`_RegQueryValueEx` (init time only; never from the
   timer callback, which runs at event time) and validates signature, version and cookie. A
   stale value after a CM reload still points to valid memory, because the CM never frees a
   block. Weaker: the pointer travels through the registry.
3. Rejected: an IOS IOP or private IOR function sent by the CM to nvme98's DCB (queues behind
   the held request, needs ILB access the CM does not have); registry polling from the timer
   callback (registry I/O at event time); a VxD service exported by the `.mpd` (an `.mpd`
   loaded by IOS has no DDB, G9).

On 9x the `.mpd` is unloaded at every removal and registers nothing, so either option leaves
nothing dangling. The 9x ordering obligation is the same: the CM sets `DOWN_QUIESCED`, waits for
the acknowledgement (the 9x timer fires 100-315 ms late on 98 SE, up to 1.5 s on Me, G9), and
only then calls `Query_Remove_SubTree`/`Remove_SubTree`. The gone deadline on 9x is a fixed value
below the shortest observed port timeout (0.10), so the acknowledgement wait must stay well
under it.

**Interaction with MD-5.** If the maintainer chooses MD-5 (i) (helper VSD), take option 1:
the VSD hosts the block, and G3's 9x receiver costs only the `Get_DDB` lookup in the `.mpd`. If
MD-5 (ii) or (iii) is chosen (no VSD), take option 2. G3 on 98 SE and Me remains open until
one of them is prototyped with a 9x CM stand-in (a WDM driver like `reenum.sys` writing the
block after the SHPC slot goes empty).

## Consequences

1. **Interface 1 (IOCTL) fails qualification item (3) on 2000 and XP x64** and is not usable
   as the evidence-2 carrier. Under saturation it arrives only after the MD-1 deadline, which
   turns every saturated surprise removal into the MD-1 residual-risk outcome.
2. **Interface 2 passes items (1)-(3) on 2000 and XP x64** at the injection points run: 8 held,
   saturated, idle, bring-up, the `RequestComplete` stage, and a late statement while `gone`.
   Ordering (2) is a CM obligation that the miniport cannot check: run E shows nvme98 accepting
   a statement sent before any cutoff. Qualification therefore stays a host-trace check per OS,
   as PLAN says.
3. Evidence 2 releases driver DMA memory on these two ports only if MD-3 is decided so that the
   memory is the driver's (option (b)): with option (a) the port frees its extensions anyway at
   removal (G5), and the statement only decides when the callers' buffers are returned.
4. PLAN 0.10 evidence 2 and TESTING "CM notification" should name interface 2 and its
   acknowledgement wait; the NT candidate `IOCTL_SCSI_MINIPORT` in the G3 row of 0.0 is
   replaced.
5. Still open: 98 SE and Me (needs a 9x stand-in and one of the 9x rendezvous options),
   XP x86, Vista, 7 x86 and 7 x64 (q35, native hot-plug: the OS's own removal races the CM;
   needs a test-signed stand-in), and real hardware (A1, MD-2).

## Decision needed (maintainer)

> Decided 2026-10-15: MD-6 adopts interface 2 on NT (PLAN.md, "Maintainer decisions"). The
> text below is the proposal as the gate wrote it.

- **MD-6 (proposed): adopt interface 2 on NT.** It needs `ExCreateCallback` and
  `ExNotifyCallback` imports from the miniport (outside the SCSIport miniport contract, as MD-3
  (b) is), and a never-freed block in the CM. Alternative: keep only the IOCTL, accepting that
  saturated removals end at the MD-1 deadline (then G3 brings nothing over MD-1 under load).
  Interface 2 stays inactive in dump mode (no `ExCreateCallback` call when `DumpMode`); the
  extra `ntoskrnl` imports did not stop the dump driver from loading on 2000 or XP x64
  (G6.md).
- On 9x, the rendezvous follows MD-5.
