**Not safe as-is. The driver is repairable for AMD64; the source does not justify a rewrite solely because Windows is 64-bit.** Its largest problems are DMA ownership, recovery, and data integrity, affecting both x86 and x64.

This was a static review of the requested files, supporting headers, the existing build log, and Microsoft/NVMe documentation. I changed no files and ran no build, driver, or tests. Findings below are ranked by severity; conditional scenarios are identified explicitly.

1. **Critical — Reset completes requests while hardware can still DMA into their buffers.**  
   [nvme2k.c:991](nvme2k-1.2.0.0/src/nvme2k.c:991), [nvme2k_nvme.c:497](nvme2k-1.2.0.0/src/nvme2k_nvme.c:497).  
   `HwResetBus` calls `ScsiPortCompleteRequest` and returns success without resetting hardware, stopping DMA, clearing queues, releasing PRP ownership, or clearing `NonTaggedInFlight`. Completion lookup has no generation validation. **Scenario:** an I/O timeout completes an SRB, Windows reuses its memory/tag, and the old NVMe command subsequently writes into that memory or completes the replacement request. The abort handler at `nvme2k.c:848` similarly reports success without aborting its target. **Fix:** quiesce/reset hardware before releasing requests; invalidate outstanding command mappings, clear all tracking, and reject stale completions. Implement abort or report its failure. [Reset contract](https://learn.microsoft.com/en-us/previous-versions/windows/hardware/storage/ff557318%28v%3Dvs.85%29).

2. **Critical — Namespace block size is decoded incorrectly; the identify structure is also malformed.**  
   [nvme2k_cpl.c:403](nvme2k-1.2.0.0/src/nvme2k_cpl.c:403), [nvme.h:219](nvme2k-1.2.0.0/src/nvme.h:219).  
   `FLBAS` selects an LBA format; it is not the block-size exponent. The driver reports format zero as 512 bytes and format one as **2 bytes**. Additionally, `Reserved1[100]` places NGUID at 128 and LBA formats at 152, rather than 104 and 128. **Scenario:** format zero actually uses 4-KiB sectors; a nominal 512-byte read causes a 4-KiB device transfer, potentially overwriting adjacent memory. **Fix:** correct offsets, obtain the exponent from the selected LBA format, validate namespace/metadata support, and add compile-time layout assertions. [Namespace fields](https://learn.microsoft.com/en-us/windows/win32/api/nvme/ns-nvme-nvme_identify_namespace_data), [LBA-size encoding](https://learn.microsoft.com/en-us/windows/win32/api/nvme/ns-nvme-nvme_lba_format).

3. **Critical — Flush completion can free a PRP page belonging to another command.**  
   [nvme2k_scsi.c:660](nvme2k-1.2.0.0/src/nvme2k_scsi.c:660), [nvme2k_cpl.c:571](nvme2k-1.2.0.0/src/nvme2k_cpl.c:571).  
   Flush submission never initializes `SrbExtension->PrpListPage`, but ordinary completion frees every value other than `0xFF`. **Scenario:** a zeroed flush extension names page zero, currently holding another request’s PRP list; subsequent allocation overwrites that live list. Separately, `nvme2k_cpl.c:138` frees an **uninitialized** `prpPageIndex` when a SMART completion has no matching SRB. **Fix:** initialize every request extension before submission; track ownership explicitly; never free a page inferred from missing or stale request state.

4. **High — Read/write length validation uses overflowing 32-bit arithmetic and mishandles zero-length commands.**  
   [nvme2k_nvme.c:598](nvme2k-1.2.0.0/src/nvme2k_nvme.c:598), [nvme2k_nvme.c:738](nvme2k-1.2.0.0/src/nvme2k_nvme.c:738).  
   `numBlocks * NamespaceBlockSize` remains 32-bit on AMD64. Large READ/WRITE(16) counts can bypass validation through overflow; the unbounded count also spills outside NVMe’s 16-bit NLB field. Zero-block READ/WRITE(10/16) becomes a **one-block** NVMe operation. **Scenario:** a zero-length WRITE with a supplied buffer unexpectedly modifies a sector. **Fix:** use checked 64-bit arithmetic, validate NLB and namespace bounds, complete zero-length commands without hardware I/O, and map the validated transfer length.

5. **High — NVMe passthrough trusts buffers before checking their lengths.**  
   [nvme2k_scsi.c:1361](nvme2k-1.2.0.0/src/nvme2k_scsi.c:1361), [nvme2k_cpl.c:209](nvme2k-1.2.0.0/src/nvme2k_cpl.c:209), [nvme2k_nvme.c:403](nvme2k-1.2.0.0/src/nvme2k_nvme.c:403).  
   Dispatch guarantees only an `SRB_IO_CONTROL` header, then reads the following passthrough structure. Completion writes `Completion[]` before validating output space. GET LOG PAGE can request more than 4 KiB despite allocating one page and setting PRP2 to zero. **Scenario:** a truncated diagnostic IOCTL causes out-of-bounds kernel access; an oversized log request produces invalid DMA descriptors. **Fix:** validate all headers, payload lengths, directions, and output capacity before access/submission; cap transfers to the actual allocation or build sufficient PRPs.

6. **High — Initialization and failure cleanup do not preserve DMA safety.**  
   [nvme2k_nvme.c:1079](nvme2k-1.2.0.0/src/nvme2k_nvme.c:1079), [nvme2k_nvme.c:1380](nvme2k-1.2.0.0/src/nvme2k_nvme.c:1380), [nvme2k.c:452](nvme2k-1.2.0.0/src/nvme2k.c:452).  
   Sanitization clears admin queue registers **before** disabling an already running controller. Later initialization failures return without disabling the newly enabled controller or cancelling its timer. Shutdown also continues clearing queue registers after a disable timeout. **Scenario:** delayed Identify DMA arrives after failed adapter discovery has released resources. **Fix:** disable and establish quiescence before changing queue addresses; centralize failure cleanup and do not release DMA memory while hardware can still access it.

7. **High — Surprise removal has no terminal “device gone” state and causes long busy waits.**  
   [nvme2k_nvme.c:39](nvme2k-1.2.0.0/src/nvme2k_nvme.c:39), [nvme2k_nvme.c:864](nvme2k-1.2.0.0/src/nvme2k_nvme.c:864), [nvme2k.c:931](nvme2k-1.2.0.0/src/nvme2k.c:931).  
   `CSTS == 0xFFFFFFFF` satisfies the “ready” test. Runtime polling does not check presence or command deadlines. Stop can busy-wait roughly **12 seconds** after removal; sanitization can wait roughly **30 seconds**. These hardware waits are bounded, **not literal infinite loops**, but runtime retry/polling has no driver-owned terminal recovery. Timer callbacks process queues even after initialization is cleared. **Fix:** detect all-ones/fatal status, stop submissions and timer activity, safely fail outstanding requests, and use bounded recovery states. Multi-second `ScsiPortStallExecution` loops also violate its documented timing restrictions. [Stall contract](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/srb/nf-srb-scsiportstallexecution).

8. **High — Advertised restart support does not restart the controller.**  
   [nvme2k.c:1041](nvme2k-1.2.0.0/src/nvme2k.c:1041), [nvme2k.c:647](nvme2k-1.2.0.0/src/nvme2k.c:647).  
   Stop disables the controller, deletes queues, and clears `InitComplete`; restart merely calls `HwInitialize`, which enables interrupts and unconditionally succeeds. **Scenario:** sleep/resume leaves the disk unusable; read/write admission still accepts the retained namespace size and submits to nonexistent queues. **Fix:** reconstruct controller/queue state using retained allocations, or stop advertising `ScsiRestartAdapter` and correctly support the port’s reinitialization path. [Adapter-control contract](https://learn.microsoft.com/en-us/previous-versions/windows/hardware/storage/ff557274%28v%3Dvs.85%29).

9. **High — Write durability and ORDERED-tag semantics are not implemented correctly.**  
   [nvme2k_nvme.c:735](nvme2k-1.2.0.0/src/nvme2k_nvme.c:735), [nvme2k_scsi.c:480](nvme2k-1.2.0.0/src/nvme2k_scsi.c:480).  
   SCSI FUA is ignored. An ORDERED request queues a Flush and immediately queues its I/O without waiting for earlier commands or the Flush. The synthetic Flush’s error is discarded, and its queue-depth increment is never decremented because it has no SRB. **Scenario:** filesystem ordering/durability expectations fail during power or tunnel loss. **Fix:** translate FUA, implement an actual ordering barrier, propagate Flush failure, and account for internal commands separately. NVMe Flush covers commands already completed before its submission; it is not a submission-queue fence. [Flush semantics](https://learn.microsoft.com/en-us/windows/win32/api/nvme/ne-nvme-nvme_nvm_commands), [FUA semantics](https://learn.microsoft.com/en-us/windows/win32/api/nvme/ns-nvme-nvme_cdw12_read_write).

10. **High — PCI configuration access occurs from forbidden SCSIport callbacks.**  
    [nvme2k.c:655](nvme2k-1.2.0.0/src/nvme2k.c:655), [nvme2k_nvme.c:1403](nvme2k-1.2.0.0/src/nvme2k_nvme.c:1403), [utils.c:759](nvme2k-1.2.0.0/src/utils.c:759).  
    `HwInitialize`, including its restart invocation, calls `ScsiPortGetBusData`/`ScsiPortSetBusDataByOffset`. Those APIs permit only FindAdapter or `ScsiSetRunningConfig`. Read helpers also ignore short results and can return uninitialized stack bytes after removal. **Scenario:** initialization/resume fails on a stricter port implementation, or absent-device config data drives bogus writes. **Fix:** move configuration work to permitted callbacks, implement `ScsiSetRunningConfig` where necessary, and check returned byte counts. [Read restrictions](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/srb/nf-srb-scsiportgetbusdata), [write restrictions](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/srb/nf-srb-scsiportsetbusdatabyoffset).

11. **Medium — Uncached allocation exceeds XP limits and alignment is assumed.**  
    [nvme2k.c:395](nvme2k-1.2.0.0/src/nvme2k.c:395), [utils.c:704](nvme2k-1.2.0.0/src/utils.c:704).  
    The first allocation is **148 KiB**, exceeding the documented XP-and-earlier 100-KiB limit. Its 84-KiB fallback still exceeds dump/hibernation limits; the documented interface permits one call per adapter. The allocator aligns offsets, not the physical base-plus-offset. **Scenario:** XP allocation/dump initialization fails; if the returned base is not page-aligned, every NVMe queue/PRP-list address is misaligned. **Fix:** choose a supported allocation budget up front, provide a small dump configuration, and align against the actual DMA address using the reserved padding. [Allocation contract](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/srb/nf-srb-scsiportgetuncachedextension).

12. **Medium — DMA configuration contains contradictory flags and overrides port limits.**  
    [nvme2k.c:244](nvme2k-1.2.0.0/src/nvme2k.c:244), [nvme2k.c:459](nvme2k-1.2.0.0/src/nvme2k.c:459).  
    Both `Dma32BitAddresses` and `Dma64BitAddresses` are set, although the former must be false with 64-bit DMA. `NumberOfPhysicalBreaks` is overwritten with 511 even if the port supplied a smaller limit. Maximum transfer size can increase from 128 KiB to 2 MiB after DMA allocation setup. **Scenario:** the advertised transfer contract exceeds the port’s configured mapping resources. **Fix:** use the named 64-bit capability constant, clear the 32-bit flag, preserve lower port limits, and establish a consistent DMA budget before allocation. **`TRUE` itself is not the bug:** WDK 7.1 defines `SCSI_DMA64_MINIPORT_SUPPORTED` as `0x01`. [Configuration contract](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/srb/ns-srb-_port_configuration_information).

13. **Medium — Fallback BAR discovery drops the high half of a normal 64-bit BAR.**  
    [nvme2k.c:287](nvme2k-1.2.0.0/src/nvme2k.c:287).  
    The 64-bit type test uses `(bar0tmp & 6) == 6`; the correct encoding is `4`. Thus BAR1 is not read for a normal 64-bit BAR. BAR sizing also occurs with memory decoding already enabled. **Scenario:** when the supplied access range is empty and BAR0 is above 4 GiB, the driver maps the wrong address. The populated PnP-resource path avoids this defect. **Fix:** prefer assigned resources; otherwise decode the BAR correctly, retain the complete physical address, and perform sizing with decoding disabled and both halves restored.

14. **Medium — Controller queue limits can produce invalid ring arithmetic.**  
    [nvme2k_nvme.c:1167](nvme2k-1.2.0.0/src/nvme2k_nvme.c:1167), [nvme2k_nvme.c:1260](nvme2k-1.2.0.0/src/nvme2k_nvme.c:1260).  
    `MQES + 1` is narrowed to `USHORT` before limiting, so `MQES == 0xFFFF` becomes zero. Smaller non-power-of-two capacities are used directly although indexing and phase logic require powers of two. **Scenario:** a capacity of 48 produces mask 47, skipping/reusing entries incorrectly. **Fix:** calculate in a wider type, select a supported power-of-two queue size, and reject invalid capabilities. Also validate 4-KiB page support and doorbell offsets against the mapped BAR length.

15. **Medium — INQUIRY misdecodes EVPD and contains a short-buffer overwrite.**  
    [nvme2k_scsi.c:69](nvme2k-1.2.0.0/src/nvme2k_scsi.c:69).  
    EVPD is read from `PageCode` bit zero instead of CDB byte one. This breaks ordinary VPD discovery and makes the `0xB1` branch unreachable. The supported-pages response checks for six bytes but writes eight. **Scenario:** normal Windows VPD queries receive standard inquiry data; a malformed page-one query with a six-byte buffer overwrites two bytes. **Fix:** use `CDB6INQUIRY3.EnableVitalProductData`, preserve the page code, and bound every response by both allocation and buffer lengths.

The specific **64-bit assessment** is considerably better than the overall safety assessment:

- I found **no active virtual-pointer-to-`ULONG` truncation**, x86 inline assembly, or x86-only intrinsic in these files. The apparent assembly is commented out.
- Queue addresses, PRP1/PRP2, and PRP-list entries retain `.QuadPart`/`ULONGLONG`. Ordinary transfers handle an offset first page, a direct second page, and subsequent separately mapped pages. **RAM above 4 GiB does not inherently break this path.**
- The WDK’s `ScsiPortConvertUlongToPhysicalAddress` argument is actually `ULONG_PTR`; the AMD64 conversion at `nvme2k.c:300` is not another truncation bug.
- Device-extension offset comments describe x86 and are wrong on x64, but allocation uses `sizeof` and access uses C members. The hardware SQ/CQ structures contain fixed-width fields and retain their intended 64-/16-byte layouts. The namespace-layout defect is architecture-independent.
- SCSIport serializes StartIo against its ISR; absent driver-owned spinlocks alone is **not** evidence of an SMP race. The demonstrated ownership/reset defects remain serious despite that serialization. [SCSIport synchronization model](https://learn.microsoft.com/en-us/windows-hardware/drivers/storage/half-duplex-mode--not-appropriate-for-shipped-products).

**SCSIport and INF:** Windows 7’s support for SCSIport does not force a rewrite. This implementation should be treated as an **INTx** miniport; it has no MSI/MSI-X integration. Leaving PnP interrupt routing to the port/HAL is appropriate. Deprecation is separate from compatibility with these historical targets.

The AMD64 INF references are internally consistent: [NVMe2K.inf:27](nvme2k-1.2.0.0/src/WDM/NVMe2K.inf:27) selects `NVMe_Inst.x64`, whose CopyFiles, Services, and ServiceBinary entries all name `NVMe2Kx64.sys`; `SourceDisksFiles.amd64` is correct. `.x64` here is part of an explicitly referenced section name, not an invalid substitute for the required Models `.NTamd64` decoration. [INF selection rules](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/creating-inf-files-for-multiple-platforms-and-operating-systems). Catalog/signature validity and installation were not tested.

**Verdict: usable with specific fixes—not usable as-is.** Retaining this codebase for XP x64/Windows 7 x64 is technically reasonable, but recovery, request ownership, namespace decoding, and DMA bounds need substantial repair. A successful AMD64 compilation or basic QEMU read/write demonstration cannot establish those properties. For the proposed hot-removable USB4/Thunderbolt endpoint, I would withhold approval until those fixes pass high-memory DMA, timeout/reset, surprise-removal, and suspend/resume validation.
